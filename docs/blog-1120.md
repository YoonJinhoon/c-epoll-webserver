# 웹 서버 동시성: 단일 스레드부터 epoll까지 왜 바뀌는가 (11/20)

> C로 웹 서버를 만드는 과제를 하고 있다. 바로 epoll부터 짜지 않고, **가장 단순한 서버부터 만들어서 직접 막혀보는** 방식으로 공부했다.
> ✅ = 실험으로 직접 확인함 / 📖 = 설명만 들음 (아직 확인 안 함)

---

## 1. 큰 그림

```
① 단일 스레드  →  연결마다 스레드  →  ② 스레드 풀  →  ③ epoll  →  ④ 하이브리드
     ✅ 실험 01         ✅ 실험 02          📖              📖
```

각 단계는 **앞 단계의 문제를 해결하려고** 나왔다. 그래서 앞 단계의 문제를 직접 겪어봐야 다음 단계가 왜 필요한지 납득이 된다.

---

## 2. 기초 단어

### fd (file descriptor)
- 그냥 **정수 번호**다 (3, 4, 5...).
- 진짜 연결 정보(주고받은 데이터, 상대 주소 등)는 **커널 안의 표**에 있다. 내 코드는 번호만 들고 있다가 `read(4, ...)`처럼 "4번 연결에서 읽어줘"라고 커널에 부탁한다.
- 포인터(메모리 주소)가 아니다. 내가 직접 따라가서 읽을 수 없고, 꼭 커널을 거쳐야 한다.

### 소켓 2종류 ✅

| 소켓 | 하는 일 | 개수 |
|---|---|---|
| **listen 소켓** | 새 연결을 받기만 한다 | 서버에 1개. 서버가 켜져 있는 동안 그대로 |
| **연결 소켓** | 클라이언트 하나와 데이터를 주고받는다 | 클라이언트마다 1개. 연결될 때 생기고 close할 때 사라짐 |

### fd와 데이터는 다르다
- **fd** = 연결의 번호. `accept`가 연결을 꺼낼 때 생긴다.
- **데이터** = 그 연결로 오가는 내용 (`GET / HTTP/1.1 ...`). `read`로 받는다.

### 서버 함수 흐름

| 함수 | 넣는 것 → 돌려받는 것 | 잠드나? |
|---|---|---|
| `socket` | → listen 소켓 fd | X |
| `bind` | 포트 번호(9000)를 소켓에 묶음 | X |
| `listen` | 연결 받기 시작 + 커널 대기열 크기(16) | X |
| `accept` | listen fd → **연결 소켓 fd** | **💤 커널 대기열이 비어 있으면** |
| `read` | 연결 fd → 데이터 | **💤 데이터가 아직 안 왔으면** |
| `write` | 연결 fd + 응답 → 보낸 바이트 수 | (보통 X) |
| `close` | 연결 fd → 연결 끝 | X |

`accept`의 정확한 뜻: **연결은 커널이 이미 받아서 대기열에 줄 세워 둔다.** `accept`는 그 대기열에서 하나를 꺼내 연결 소켓 fd를 돌려주는 함수다. 대기열이 비어 있으면 올 때까지 잠든다.

## 3. 실험 방법

터미널 3개를 쓴다.

| 터미널 | 명령 | 하는 일 |
|---|---|---|
| **A** | `./server` | 서버 |
| **B** | `nc localhost 9000` | 연결만 하고 가만히 있는 **느린 클라이언트** |
| **C** | `curl localhost:9000` | 연결하고 요청을 자동으로 보내는 **정상 클라이언트** |

순서: A → B → C. 서버 로그에 번호를 붙여서 **스레드가 지금 어디서 멈췄는지** 볼 수 있게 했다.

```
[3] accept💤 → [4] fd 생김 → [5] read💤 → [6] 데이터 받음 → [7] 응답 보내고 close → 다시 [3]
```

---

## 4. 실험 01: 단일 스레드 ✅

스레드가 main 하나뿐이다. main이 accept, read, write를 전부 직접 한다.

**결과**
- B가 연결되면 서버는 `[5] read`에서 B의 데이터를 기다리며 잠든다.
- 이때 C를 실행하면 **C 화면에는 아무것도 안 뜬다.**
- B에 `GET / HTTP/1.1`을 치자 B가 응답을 받고, 그다음에야 C가 바로 처리됐다.

**원인:** 단일 스레드가 `read()`에서 B의 데이터를 기다리며 잠들어 있어서, accept로 돌아가지 못한다.

**C는 버려지지 않았다:** 서버가 자는 동안에도 **커널이** C의 연결과 요청 데이터를 대기열에 보관하고 있었다. 그래서 서버가 accept로 돌아가자마자 C는 잠들지 않고 바로 처리됐다.

**덤으로 본 것**
- B와 C 둘 다 연결 소켓 fd = 4를 받았다. B의 fd 4가 close되면서 번호가 비었고, C가 그 번호를 다시 받은 것이다.
- 응답 116바이트 = 상태줄 17 + 헤더 26 + 20 + 19 + 빈 줄 2 + 본문 32 (`\r\n`은 2바이트). 출력된 숫자를 손으로 계산해서 맞춰보는 것도 검증이다.
- 🔎 B에서 엔터를 **한 번만** 쳤는데 서버가 응답했다 (15바이트). 진짜 HTTP 요청은 빈 줄로 끝나야 하는데? → 다음에 파서를 만들 때 다룬다.

**해결책 후보**
- timeout (일정 시간 뒤 B 끊기) = **방어**. 하지만 기다리는 동안 C는 여전히 멈춰 있다.
- 스레드 추가 = **동시성** → 실험 02

## 5. 실험 02: 연결마다 스레드 1개 ✅

main은 **accept만** 하고, 연결 소켓 fd를 새로 만든 담당 스레드(T1, T2...)에게 넘긴다. read → write → close는 담당 스레드가 하고, 함수가 끝나면 스레드도 끝난다.

```
main: accept💤 → T1 만들기 → accept💤 → T2 만들기 → accept💤 ...
T1:              read💤 (B 기다림)...
T2:                                     read → write → close (C 처리 끝)
```

**결과:** B가 가만히 있어도 C가 바로 응답을 받았다.

**증거 (로그)**
- `[T2] [6] 77 바이트 받음`, `[T2] [7] 응답 보냄` → C는 처리됐다.
- `[T1] [5] read() 호출` 이후 **`[T1] [6]`이 없다** → B 담당 스레드는 아직 잠들어 있다.
- 둘이 같이 있어야 "B가 C를 막지 않았다"가 증명된다. **없는 줄도 증거가 된다.**
- C가 fd 5를 받았다 (실험 01에서는 4). B의 fd 4가 아직 열려 있다는 뜻이다.
- 로그 순서가 섞였다 (`[main] [3]`이 `[T1] [5]`보다 먼저). 스레드들이 동시에 돌아서 누가 먼저 찍을지는 매번 다르다.

**약점 📖:** 느린 클라이언트 10,000개가 붙으면 스레드도 10,000개가 된다. 스레드마다 자기 스택(리눅스 기본 8MB 예약)이 있다. **일은 안 하고 `read`에서 잠만 자면서 메모리를 잡고 있는다.**

## 6. 스레드 풀 📖

스레드를 **미리 정해진 수만큼만**(예: 4개) 만들어 두고 재사용한다.

```
main: accept → 연결 fd를 [일감 대기열]에 넣음 → accept → ...
W1~W4 (Worker): 대기열에서 fd 하나 꺼냄 → read → write → close → 다시 대기열로
```

**대기열은 2개다**

| | 들어 있는 것 | 누가 넣나 | 누가 꺼내나 |
|---|---|---|---|
| ① 커널 대기열 | accept 전의 연결 | 커널 | main (`accept`) |
| ② 일감 대기열 | accept 후의 연결 fd (정수) | main | Worker |

- **스레드 풀** = 스레드 묶음 (W1~W4). **대기열** = 일감(fd)을 쌓아두는 곳. 둘은 다른 것이다.

**약점:** 느린 클라이언트가 **4개** 붙으면 W1~W4가 전부 `read`에서 잠든다. C는 main이 accept해서 연결은 되지만, fd가 ② 일감 대기열에서 Worker를 기다린다. → 다시 막힌다.

---

## 7. 세 방식의 공통 원인

| 방식 | 약점 |
|---|---|
| 단일 스레드 | B 하나가 잠들면 전부 막힘 |
| 연결마다 스레드 | 클라이언트 수만큼 스레드가 늘어남 → 메모리 |
| 스레드 풀 | 느린 클라이언트가 스레드 수만큼 오면 다시 막힘 |

**공통 원인:** 스레드가 `read`에서 클라이언트 데이터를 기다리며 잠든다.
= **스레드 1개가 클라이언트 1개에 묶여서, 그 클라이언트가 데이터를 보낼 때까지 아무것도 못 한다.**

## 8. epoll 📖

**epoll = event poll.** "이벤트(데이터 도착 등)가 생긴 fd를 알려준다."

아이디어: **데이터가 도착한 fd만 골라서 read 한다.** `read`는 데이터가 없을 때만 잠드니까, 이미 온 fd만 읽으면 `read`에서 절대 잠들지 않는다.

```
main: epoll_wait💤  ← 등록한 fd 중 아무거나 데이터 오면 깨워달라고 하고 잠듦
커널: (C가 보냄) → "5번에 왔어"
main: read(5) → write → close → 다시 epoll_wait💤
      (B는 데이터를 안 보냈으니 커널이 4번을 알려주지 않음 → read(4)를 부를 일이 없음)
```

- 주기적으로 계속 물어보는 게 아니다. `epoll_wait`에서 **잠들어 있다가 커널이 깨워준다.**
- 기본 epoll 서버는 **main 스레드 하나**가 accept와 read/write를 전부 한다.

| | 잠드는 곳 | 깨어나는 조건 |
|---|---|---|
| 스레드 풀 | `read(4)` | fd 4 **하나**에 데이터가 와야 |
| epoll | `epoll_wait` | 등록한 fd 중 **아무거나** 데이터가 오면 |

## 9. 오늘 배운 검증 방법

1. **예측 → 관찰:** 실행 전에 로그가 어디서 멈출지 예측하고, 실행 후 맞춰본다.
2. **없는 줄도 증거:** "일어났어야 하는데 안 일어난 것"(`[T1] [6]`이 없음)도 본다.
3. **숫자 맞춰보기:** 출력된 숫자(116바이트)를 손으로 계산해서 일치하는지 본다.
