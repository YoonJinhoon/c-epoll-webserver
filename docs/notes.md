## 스레드 vs 함수
- **함수**: 적혀 있는 코드(명령어 묶음). 스스로 움직이지 않는다.
- **스레드**: 그 코드를 실제로 실행하고 있는 흐름. 자기 스택 · 레지스터 · "지금 몇 번째 줄"(PC)을 가진다.
- PintOS `thread_create(name, prio, function, aux)` → 스레드를 만들 때 **함수를 건네준다.**
- 같은 함수를 스레드 10개가 동시에 실행할 수 있다 (각자 자기 스택, 각자 다른 줄).
- 내 첫 문장 (11/20): "스레드는 실행 흐름이다. 함수는 기능이다." → 앞은 정확, 뒤는 둘의 **관계**가 빠짐.
- ✅ 고친 문장 (11/20): "함수는 코드이고, 스레드는 함수를 실행하는 흐름이다. 그래서 같은 함수를 여러 스레드가 동시에 실행할 수 있다."

## 진행 상황은 누가 · 어디에 저장하나
| | 누가 | 어디에 |
|---|---|---|
| 스레드 풀 | **OS 가 자동으로** (context switch) | 각 스레드의 스택 (지역변수) |
| epoll | **내가 직접** | 연결마다 `struct conn` |

→ 스레드 풀 코드를 epoll 로 바꾸면 "사실상 새로 쓰는 셈" = OS 가 해주던 저장을 코드 전체에서 내가 직접 하도록 바꾸는 것.
→ 기다림과 무관한 부분(MIME, 라우팅, **조각 입력에 맞춘 파서**)은 재사용 가능.

## 소켓
- 소켓도 **fd** 다 (PintOS 파일 fd 와 같은 개념) → `read` / `write` 로 다룬다.
- fd = **정수 번호** (3, 4, 5...). 진짜 연결 정보는 커널 표에 있고, 코드는 번호만 들고 `read(4, ...)`처럼 커널에 부탁한다. 포인터(메모리 주소) 아님.
- **listen 소켓**: 새 연결을 받기만 하는 소켓. 서버에 1개.
- **연결 소켓**: `accept()` 가 클라이언트마다 새로 만들어 주는 소켓. 요청 · 응답은 여기로.
- **TCP 연결**: 클라이언트 프로그램(브라우저, curl) ↔ 서버 프로그램. 데이터를 순서대로, 빠짐없이 전달.

## read() 반환값 (단위: 바이트)
| 반환값 | 의미 |
|---|---|
| `> 0` | 그만큼 읽음. **요청한 것보다 적을 수 있음** (조각나서 온다) |
| `0` | 상대가 연결을 닫음 |
| `-1` | 에러. non-blocking 소켓에서 `errno == EAGAIN`(Error: try AGAIN) 이면 "아직 없음" |

잠드는 일은 `read()` 코드가 아니라 **커널**이 한다 (PintOS 시스템 콜처럼).

## 처리 단계 vs 이벤트
이벤트 = fd 에서 무언가를 **할 수 있게 된** 변화. 바깥 세계(네트워크)를 기다리는 일에만 있다.

| 서버가 하려는 일 | 가능하게 하는 이벤트 | 소켓 |
|---|---|---|
| 새 연결 받기 (`accept`) | 새 연결 도착 | listen |
| 요청 읽기 (`read`) | 읽을 데이터 도착 | 연결 |
| 응답 만들기 | **없음** (내부 계산) | - |
| 응답 보내기 (`write`) | 보낼 공간 생김 | 연결 |
| 정리 | 상대가 끊음 | 연결 |

## 실험 01: 단일 스레드 서버 (11/20)
설정: A `./server` → B `nc localhost 9000` (연결만) → C `curl localhost:9000` (자동 요청)
흐름: `[3] accept💤 → [4] → [5] read💤 → [6] → [7] → [3]` (💤 = 스레드가 잠드는 곳)

- 예측 3개 모두 맞음: B 연결 → A `[5]`에서 멈춤 / C 멈춤 / B가 보내면 C가 바로 처리됨
- 본 것: B가 가만히 있을 때 C도 가만히 있음 → 정확히는 **C 화면에 응답이 안 뜸.** C의 `[4]`는 B의 `[7]` 뒤에야 찍힘
- ✅ 원인: `read()`에서, 연결된 클라이언트(B)의 요청 데이터가 올 때까지 서버의 단일 스레드가 잠들어 있음
- C는 버려지지 않는다: `listen(fd, 16)` → **커널이 대기열**에 연결과 데이터를 보관. `accept`는 대기열에서 하나 꺼내는 함수
- ✅ listen 소켓(fd 3)은 서버가 켜져 있는 동안 그대로, 연결 소켓(fd 4)은 클라이언트마다 생겼다 사라짐 (번호 재사용)
- ✅ 그래서 (해결책): (1) 일정 시간 지나면 B 연결 끊기 (timeout) 또는 (2) 스레드 추가
  - timeout = **방어** (느린 클라이언트가 서버를 붙잡는 공격 막기). 기다리는 동안 C는 여전히 대기 → 동시성 해결은 아님
  - 스레드 추가 = **동시성** → 다음 단계 ② 스레드 풀
  - 응답 116바이트 = 상태줄 17 + 헤더 26+20+19 + 빈 줄 2 + 본문 32 (`\r\n`은 2바이트)
- 🔎 다음 단계 떡밥: B에서 엔터 **한 번**만 쳤는데 응답이 옴 (15바이트). 진짜 요청은 빈 줄로 끝나야 함 → 파서

## 실험 03: 스레드 풀, Worker 2개 (11/21)
- 시작: main은 accept💤 (①이 빔), W1·W2는 ②💤 (②가 빔). 스레드 3개 모두 잠듦
- B1 연결 → main⏰ fd 4 → ② → W1⏰ → read(4)💤 / B2 연결 → fd 5 → W2 → read(5)💤 (예측 "W2가 깬다" ✅)
- C 연결 → `[main] ⏰ ①에서 연결 꺼냄 -> fd 6 생김` **찍힘** (예측 "안 찍힌다" ❌) → fd 6은 ②에서 대기, 꺼내는 Worker 줄이 **없음**
- ✅ 내 말: "C는 연결은 됐지만 처리는 안 됐다. 왜냐하면 처리해줄 Worker 스레드가 없기 때문이다." (W1은 B1에, W2는 B2에 물려 있음)
- 연결 = main(accept) 담당 / 처리 = Worker(read → write → close) 담당. **다른 단계다**
- Worker가 자는 곳 2개: ②가 비었을 때, read에서 요청을 기다릴 때

## 실험 04: epoll, 스레드 1개 (11/23)
- 등록(epoll_ctl): 지켜볼 fd를 커널의 목록에 올림. 목록 자체도 fd(4)다. 순서 없음 (누가 먼저 보낼지 모르니 정렬 불필요)
- main은 `epoll_wait`에서 잠들고, **커널이** 등록된 fd를 지켜보다가 일이 생긴 fd를 알려주며 깨운다
- 일은 2종류: listen fd → 새 연결(accept 후 새 fd 등록) / 연결 fd → 요청 데이터(read → write → close → 해제)
- B1(fd 5), B2(fd 6), C(fd 7) 연결 → `⏰ fd 7에 요청 데이터 도착`만 찍힘, fd 5·6은 한 번도 read 안 함 (없는 줄 증거)
- 테스트: 느린 클라이언트 2개 PASS, **100개도 PASS**
- ✅ 내 3줄:
  1. 느린 클라이언트의 read에 main 스레드가 묶이지 않았고, 그래서 마지막에 연결·요청한 C가 응답받았다
  2. main은 등록된 느린 클라이언트 2개에게서 처리할 게 없어서 (epoll_wait에서) 잠들었고, 커널이 C의 요청 데이터 도착을 알려줬다
  3. epoll은 연결된 클라이언트가 실제로 요청했을 때만 반응한다. **스레드 풀은 스레드 하나가 클라이언트 1개를, epoll은 스레드 하나가 매우 많은 클라이언트(한계: fd 개수·메모리)를 맡는다**

## S1: 요청을 끝까지 읽기 (11/23)
- 서버 입장에서 데이터는 **끝없이 이어지는 바이트 흐름**. 경계가 없어서 서버가 "요청 하나가 다 왔다"를 스스로 판단해야 한다
- HTTP 요청 = 요청 라인 + 헤더 + **빈 줄(`\r\n\r\n`)** + (POST면 본문). 빈 줄 = 머리 끝 표시
- `\r`(13)과 `\n`(10)은 화면에선 안 보이지만 바이트로는 다른 글자. 터미널 엔터는 `\n`만 → `nc -C`(CRLF)로 `\r\n` 보내기
- 커널(TCP)이 조각의 순서를 맞춘 뒤 read로 넘겨준다
- 연결마다 보관함(`struct conn`: fd, buf[8192], len). read한 조각은 커널을 떠나 보관함에 있다. 보관함을 같이 쓰면 다른 클라이언트의 조각과 섞인다
- `len` = 지금까지 모인 총량 (0~8192). 더해간다
- ✅ 내 말: "서버는 데이터 조각이 올 때마다 request_head_end()를 호출한다. 반환값이 0이면 아직 덜 왔음, 0이 아니면 (요청 머리가) 다 왔음이고 그 값은 머리 끝의 위치 → 이제 응답할 타이밍"
- ✅ 조각 테스트 때 conn_on_data는 2번 불림: `GET / HT` → 0, `TP/1.1...\r\n\r\n` → 0 아님
- 실험 04는 FAIL: \r\n\r\n을 찾지도 않고 read 한 번에 응답했기 때문

## S2: 요청 라인 파싱 (11/23)
**목적:** 요청이 다 왔는지(S1)만 보던 서버가, **무슨 요청인지** 알아내게 하기. S3(파일 고르기)와 S5(백엔드 고르기)가 둘 다 S2가 꺼낸 **경로**를 쓴다.

**개념**
- 파싱 = 쪼개서 의미를 꺼내는 것
- 요청 라인 = 머리의 첫 줄 = `메서드 공백 경로 공백 버전`, 정확히 3조각
- 응답 = 상태 줄 + 헤더 + 빈 줄 + **본문**(curl 화면에 찍히는 것). 요청과 같은 모양
- 상태 코드는 첫 자리만: 2xx 성공 / 4xx 클라이언트 잘못 / 5xx 서버 잘못
- 경로(`/hello`)는 클라이언트가 적어 보낸 글자일 뿐. 실제 파일이 있는지는 S2가 확인하지 않는다 (S3)

**서버 흐름 (S1 + S2)**
1. 연결이 오면 → 보관함 만들기
2. 조각이 오면 → 보관함에 붙이고 "머리가 다 왔나?" (`request_head_end`)
3. 머리가 다 오면 → `request_parse_line`으로 3조각 쪼개기
   - 규칙에 안 맞으면 → **400**
   - GET/POST가 아니면 → **501** (진훈 직접 작성)
   - 그 외 → **200** + `method= / path= / version=` 본문
4. 응답 후 → 닫고 보관함 버리기

**검증**
| 통과 기준 | 결과 |
|---|---|
| ① `GET /hello` → 200 + 이름표 3줄 | PASS (손으로 + 스크립트) |
| ② 3조각 아님 → 400 | PASS |
| ③ `HELLO` → 501 | PASS |
| ④ `POST` → 200 | PASS |
| 단위 테스트 9개 (`request_parse_line`) | PASS |

**배운 것 (검증)**
- 요청을 **통째로 돌려줘도** 같은 글자가 나온다 → 쪼갰다는 증거가 안 됨 → **이름표**를 붙여 돌려받기 (진훈이 찾은 구멍)
- 규칙(모양)은 통과하지만 의미가 틀린 요청: `HELLO /hello HTTP/1.1` → 200이 나옴 (진훈이 찾은 버그) → 501로 고침
- 새 기능을 추가해도 기존 테스트 ①②는 원래 PASS → **새 기능을 검사하는 테스트(③④)를 따로** 추가해야 함
- `make`가 실패하면 옛날 실행 파일이 남는다 → make가 에러 없이 끝났을 때만 테스트

**배운 것 (코드)**
- `strcmp(a, b) == 0` = 같다, `!= 0` = 다르다
- "A도 아니고 B도 아니면" = `조건A && 조건B` **하나**. `else if` 두 개로 나누면 "A가 아니거나 B가 아니면"이 되어 GET도 501로 감
- 추측해서 바꿔보기(`!=` ↔ `==`) 대신 **값을 넣고 한 줄씩 따라가기**
- 컴파일 에러는 **첫 번째 error만** 읽기 (`파일:줄:칸`)
- `.c`는 고치면 `make` 필수, `.sh`는 저장만 하면 반영

## S3: 정적 파일 (11/23~24)
- 정적 파일 = 미리 만든 파일을 그대로 보냄 / 동적 응답 = 요청마다 계산. 루트 디렉토리 = `www` (서버 켤 때 인자)
- 실제 파일 = **루트 + 경로** (`www` + `/index.html`). 경로는 클라이언트가 적어 보낸 글자일 뿐 → 서버가 확인해서 없으면 **404**
- 응답에는 항상 상태 코드가 있다. 상태 줄 = 응답의 첫 줄. 헤더 = `이름: 값`. `curl -i`(include)로 같이 보기
- **경로 탈출:** `/../src/main.c` → `www/../src/main.c` = 소스 코드가 털림 (직접 재현). `path_is_safe`: 경로 조각에 `..`이 있으면 **403**. 설계 선택: 안전한 `..`(`/img/../index.html`)도 막음. 브라우저는 `..`을 미리 정리해서 보내므로 정상 사용자는 영향 없음
- **MIME 타입** = `대분류/소분류` (text/html, image/png, 기본값 application/octet-stream). `/`는 경로가 아니라 칸막이. `Content-Type: text/plain`이면 크롬이 HTML을 글자로 보여주고, `text/html`이면 웹페이지로 그림. octet-stream(= 그냥 바이트)이면 다운로드만 함 (모르는 걸 화면에 그리는 게 더 위험)
- `mime_type` (진훈 작성): `strrchr`(뒤에서부터)로 마지막 점 → `strcmp`로 비교 → return. 기본값 = 아무것도 안 맞을 때 쓰는 값. `strchr`(앞에서부터)였다면 `my.page.html`이 FAIL
- 약점: 대문자 확장자(`.HTML`, `.PNG`)는 strcmp가 다르다고 봐서 기본값 → 다운로드됨
- 크롬이 연결을 2개 열었던 이유: 페이지 + favicon, 그리고 우리 서버는 응답마다 연결을 닫음(Connection: close) → 미리 하나 더 열어둠
- ✅ 내 3줄:
  1. 없는 파일 → 404 / 확장자에 맞는 Content-Type으로 응답 / 경로에 `..` → 403
  2. mime_type은 파일 이름을 받아서 뒤에서부터 처음 나오는 점부터를 확장자로 보고 strcmp로 비교해 MIME 글자를 return한다 (+ 파일 찾기는 www + 경로, `..` 검사는 path_is_safe가 따로)
  3. `..`이 들어간 경로는 예외 없이 403 (브라우저는 미리 정리해서 보내므로 정상 사용자는 안 막힘)

## Git: 로컬 vs 원격
- `git checkout -b X` 는 **로컬에만** 브랜치를 만든다. GitHub 에 생기는 건 `git push -u origin X` 때.
