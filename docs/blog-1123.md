## 4. 실험 04: epoll ✅

### 구조
스레드는 **main 하나뿐**이다. main 하나가 연결 받기와 요청 처리를 전부 한다.

| 함수 | 하는 일 |
|---|---|
| `epoll_create1` | 커널 안에 **"지켜볼 fd 목록"**을 만든다. 목록 자체도 fd다 (그래서 첫 연결이 fd 4가 아니라 5를 받았다) |
| `epoll_ctl` | fd를 목록에 **하나씩** 등록하거나 해제한다 |
| `epoll_wait` | 목록 번호만 넣고 잠든다. 등록된 fd 중 **아무거나** 할 일이 생기면 깨어나고, **할 일이 생긴 fd들**을 돌려받는다 |

`read(fd)`와 비교하면:

| 함수 | 지켜보는 것 | 잠드는 조건 |
|---|---|---|
| `read(fd)` | fd **1개** | 그 fd에 데이터가 없으면 |
| `epoll_wait` | 등록된 fd **여러 개** | 등록된 fd **전부** 할 일이 없으면 |

- "잠든다" = 함수를 불렀는데 아직 끝나지 않은 상태
- 지켜보는 건 main이 아니라 **커널**이다. main은 자고 있다
- 목록에는 순서가 없다. 누가 먼저 데이터를 보낼지 예측할 수 없으니 정렬할 필요가 없다

이 서버에서 "할 일"은 두 종류뿐이다.

| 등록된 fd | 생기는 일 | main이 하는 것 |
|---|---|---|
| listen 소켓 | 새 연결이 옴 | accept → 새 fd를 목록에 등록 |
| 연결 fd | 요청 데이터가 옴 | read → write → close → 목록에서 해제 |

### 실험: 느린 클라이언트 2개(B1, B2) + C
```
[main] ⏰ listen fd에 새 연결 -> accept -> fd 5 생김, 등록 (지켜보는 연결 1개)   ← B1
[main] epoll_wait -> 잠듦💤 (지켜보는 연결 1개)                                    ← B1에 묶이지 않고 돌아옴
[main] ⏰ listen fd에 새 연결 -> accept -> fd 6 생김, 등록 (지켜보는 연결 2개)   ← B2
[main] ⏰ listen fd에 새 연결 -> accept -> fd 7 생김, 등록 (지켜보는 연결 3개)   ← C
[main] epoll_wait -> 잠듦💤 (지켜보는 연결 3개)
[main] ⏰ fd 7에 요청 데이터 도착                                                  ← 커널이 깨움
[main]   read(7) -> 77 바이트, 안 잠들고 바로 읽음
[main]   fd 7 응답 보내고 close (지켜보는 연결 2개)
```

- 실험 01에서는 B가 연결되자 main이 `read(B)`에서 꼼짝 못 했다. 이번엔 B1을 목록에 올려두고 **바로 epoll_wait로 돌아왔다.**
- **"커널이 지켜본다"가 보이는 순간:** main이 자고 있는 동안, 누군가 "B1, B2는 조용하고 fd 7에 데이터가 왔다"는 걸 알아채서 main을 깨웠다. 그게 커널이다.
- **없는 줄:** fd 5, 6에 대한 `요청 데이터 도착`이 없다. main은 B1, B2를 **한 번도 read하지 않았다.**

### 검증 스크립트
- 느린 클라이언트 2개 → **PASS ✅** (예측과 일치)
- 궁금해서 100개로 돌려봄 → **PASS ✅**. 스레드 1개로 느린 클라이언트 100개를 버텼다. 스레드 풀(Worker 2)은 2개에서 무너졌다.

### 내 말로 3줄
1. **본 것:** 느린 클라이언트의 read에 main 스레드가 묶이지 않았고, 그래서 마지막에 연결하고 요청한 C가 응답받았다.
2. **원인:** main은 등록된 느린 클라이언트 2개에게서 처리할 게 없어서 epoll_wait에서 잠들었고, 커널이 C의 요청 데이터 도착을 알려줬다.
3. **그래서:** epoll은 연결된 클라이언트가 실제로 요청했을 때만 반응한다. **스레드 풀은 스레드 하나가 클라이언트 1개를, epoll은 스레드 하나가 매우 많은 클라이언트(한계: fd 개수와 메모리)를 맡는다.**

## 7. S1: 요청을 끝까지 읽기 (진짜 서버 `src/` 시작) ✅

실험 코드(`experiments/`)는 버리고, 제출할 서버(`src/`)를 epoll로 짓기 시작했다.

### 왜
실험 01에서 nc로 엔터를 **한 번만** 쳤는데 서버가 바로 응답했다. 서버가 요청이 **끝났는지 확인하지 않고**, read 한 번에 들어온 것만 보고 응답했기 때문이다.

### 개념
- **서버 입장에서 데이터는 끝없이 이어지는 바이트 흐름이다.** "여기까지가 요청 하나"라는 경계가 없다. 그래서 서버가 스스로 판단해야 한다.
- HTTP 요청 = **요청 라인 + 헤더 + 빈 줄 + (POST면) 본문**. 빈 줄(`\r\n\r\n`)이 **머리 끝** 표시다.
  ```
  GET / HTTP/1.1\r\n            ← 요청 라인
  Host: localhost:9000\r\n      ← 헤더
  Accept: */*\r\n               ← 헤더
  \r\n                          ← 빈 줄 = 머리 끝
  ```
- `\r`(13)과 `\n`(10)은 화면에선 안 보이지만 **바이트로는 다른 글자**다. HTTP는 줄 끝에 둘 다(`\r\n`) 쓴다. 터미널에서 엔터를 치면 `\n`만 가서, nc로 실험할 때는 `nc -C`(CRLF)를 써야 한다.
- 데이터는 조각나서 올 수 있다. 조각의 크기는 정해져 있지 않다. 하지만 **커널(TCP)이 순서를 맞춘 뒤에 read로 넘겨준다.** 서버 코드는 순서 걱정을 안 해도 된다.

### 설계: 연결마다 보관함
```c
struct conn {
    int    fd;          // 어느 연결의 보관함인지
    char   buf[8192];   // 지금까지 도착한 조각들을 이어 붙인 것
    size_t len;         // 지금까지 모인 바이트 수 (0 ~ 8192, 더해간다)
};
```
- read로 꺼낸 조각은 **커널을 떠나 보관함에** 있다. 아직 read하지 않은 조각은 커널에 있다.
- 보관함을 **연결마다 따로** 둬야 한다. 하나를 같이 쓰면 X가 보낸 `GET / HT`와 C가 보낸 요청이 섞여서 `GET / HTGET /c HTTP/1.1...`이 된다.
- `buf`는 **흐름을 요청 단위로 끊기 위한 작업대**다.

```
연결이 생기면  → 그 연결의 보관함 1개 만듦
조각이 오면    → 그 연결의 보관함 끝에 붙임 + "머리가 다 왔나?" 물어봄
연결이 끝나면  → 보관함 버림
```

"머리가 다 왔나?"를 묻는 함수: `request_head_end`. 반환값이 **0이면 아직 덜 옴(기다림), 0이 아니면 머리가 다 옴(그 값은 머리 끝의 위치) → 이제 응답할 타이밍.**

중요한 점: 덜 왔을 때 main이 그 연결을 기다리며 **잠들면 안 된다.** 그러면 실험 01로 돌아간다. 보관함에 넣어두고 epoll_wait로 돌아가서 다른 연결을 처리한다.

### 검증
- 통과 기준: *"`nc -C`로 요청을 두 조각으로 나눠 보낼 때, 첫 조각만 보낸 시점에는 응답이 없고, 빈 줄까지 보낸 뒤에 응답이 정확히 1번 오면 통과. 그동안 다른 클라이언트는 막히지 않는다."*
- 예측: S1 서버 PASS, 실험 04 서버 PASS → **실험 04는 FAIL ❌ (틀림).** 실험 04는 `\r\n\r\n`을 찾지도 않고 첫 조각(`GET / HT`)이 왔다는 이유만으로 응답했다.
- 단위 테스트 = **함수 하나만 떼어서**, 서버를 띄우지 않고 입력 → 기대 출력을 확인. (빌드할 때 `main.c`가 빠져 있다. 그게 "단위"라는 뜻)
- 조각 테스트 때 서버 로그: 조각 1 → 0(기다림), 조각 2 → 0이 아님(응답). `보관함 8 → 39 바이트`처럼 len이 더해진다.

### 틀릴 수 있는 곳 (직접 찾음)
1. 컴파일러 경고: `write`의 반환값을 무시함. **read가 덜 읽을 수 있듯이 write도 덜 보낼 수 있다.** 확인 안 하면 응답이 잘릴 수 있다. → S3에서 "다 보낼 때까지 반복"으로 고침
2. 머리가 8192바이트를 넘으면 설명 없이 연결을 끊는다. HTTP 규칙대로면 오류 응답(431/400)을 보내야 한다. → S6

## 8. S2: 요청 라인 파싱 ✅

### 왜
S1 서버는 요청이 **다 왔는지만** 보고, **무슨 요청인지는** 안 봤다. 다음 단계에서 파일을 고르려면(S3) 경로가 필요하다.

### 개념
- **파싱** = 쪼개서 의미를 꺼내는 것
- 요청 라인 = `메서드 공백 경로 공백 버전`, **정확히 3조각**
- 응답도 요청과 같은 모양: 상태 줄 + 헤더 + 빈 줄 + **본문**(curl 화면에 찍히는 것)
- 상태 코드는 첫 자리만 알면 된다: **2xx 성공 / 4xx 클라이언트 잘못 / 5xx 서버 잘못**
- **응답에는 항상 상태 코드가 있다.**

| 상태 코드 | 언제 |
|---|---|
| 400 | 요청 라인이 규칙(3조각, 대문자 메서드, `/`로 시작하는 경로, `HTTP/`로 시작하는 버전)에 안 맞음 |
| 501 | **모양은 규칙에 맞지만, GET/POST가 아닌 메서드** |
| 200 | 규칙에 맞고 처리 성공 |

### 서버 흐름 (S1 + S2)
```
1. 연결 → 보관함 만들기
2. 조각 → 보관함에 붙이고 "머리가 다 왔나?"
3. 머리 다 옴 → 3조각으로 쪼개기 → 400 / 501 / 200
4. 응답 → 닫고 보관함 버리기
```

### 검증에서 내가 찾은 구멍
처음 통과 기준은 "`GET /hello`를 보내면 본문에 `GET /hello HTTP/1.1`이 오면 통과"였다. 그런데 의문이 들었다. **서버가 쪼개지 않고 받은 줄을 통째로 돌려줘도 똑같이 나온다.** 그러면 쪼갰는지 구분이 안 된다.
→ 조각마다 **이름표**를 붙여 돌려받기로 했다.
```
method=GET
path=/hello
version=HTTP/1.1
```

### 내가 찾은 버그
`HELLO /hello HTTP/1.1`을 네 규칙에 하나씩 대입해보니 **전부 통과 → 200**이 나온다. 하지만 HELLO라는 메서드는 없다. **모양은 맞지만 의미가 틀렸다.** → 501로 고치기로 했다.

### 내가 직접 쓴 첫 코드
"메서드가 GET도 아니고 POST도 아니면 501."

| 시도 | 코드 | 결과 |
|---|---|---|
| 1 | `else if (GET이 아니면) 501` / `else if (POST가 아니면) 501` | GET이 "POST가 아니다"에 걸려서 **501** → 테스트 ① FAIL |
| 2 | `!=`를 `==`로 뒤집어봄 (추측) | 여전히 FAIL |
| 3 | 괄호를 잘못 닫음 | **컴파일 에러** → 그런데 테스트를 돌려버림 → **옛날 실행 파일**을 검사함 |
| 4 | `else if (GET이 아니고 && POST도 아니면) 501` | **PASS** |

배운 것:
- "A도 아니고 B도 아니면" = **조건 하나에 `&&`**. `else if` 두 개로 나누면 "A가 아니거나 B가 아니면"이 된다
- 추측해서 바꿔보기 대신, **값을 넣고 한 줄씩 따라가기**
- 컴파일 에러는 **첫 번째 error만** 읽는다 (`파일:줄:칸`)
- `make`가 실패하면 옛날 실행 파일이 남는다. **make가 에러 없이 끝났을 때만 테스트**
- `.c`는 고치면 `make` 필수, `.sh`는 저장만 하면 반영
- 501을 추가해도 기존 테스트 ①②는 원래 PASS였다. **새 기능을 검사하는 테스트를 따로** 추가해야 한다 (③ HELLO → 501, ④ POST → 200)

## 9. S3: 정적 파일 (진행 중)

- **정적 파일** = 미리 만들어둔 파일을 **그대로** 보냄 (누가 언제 요청해도 같음). **동적 응답** = 요청마다 서버가 계산해서 만듦
- **루트 디렉토리** = 정적 파일을 모아둔 폴더(`www`). 서버를 켤 때 인자로 준다: `./webserver 9000 www`
- 서버는 요청 경로 앞에 루트 폴더 이름을 붙여서 실제 파일 위치를 만든다. `/index.html` → `www/index.html`
- S3부터 `GET /hello`는 **404**가 된다. 클라이언트는 `/hello`를 적어 보냈지만, 서버가 확인해보니 `www/hello`가 없기 때문이다. **경로는 클라이언트가 적어 보낸 글자일 뿐이다.**
- 서버의 동작이 바뀌면 테스트도 같이 바뀌어야 한다 (GET은 이제 파일을 보내므로, 파싱 확인 테스트를 POST로 바꿈)

S3는 세 조각으로 나눠서 진행한다: **a** 파일 보내기와 404 / **b** 확장자 → MIME 타입 (직접 작성 예정) / **c** `www` 밖으로 나가는 경로 막기 (403)

### 메모리 검사를 AI에게 맡겨도 되는지 판단할 근거
1. 내가 **직접 다시 돌릴 수 있나** (명령과 출력이 있나)
2. **버그를 일부러 넣으면 잡히나** (검사 도구도 FAIL을 한 번 봐야 믿을 수 있다)
3. **어떤 요청으로 검사했나** (ASan은 실행된 코드만 검사한다)

## 10. 오늘의 학습 메모
- 실험으로 **직접 본 것**은 이틀이 지나도 남는다. **표로 읽은 것**은 몇 시간 만에 잊는다 (`epoll_wait`를 아침에 배우고 오후에 잊음)
- 반복이 기억을 만드는 게 아니라, **잊을 만할 때 애써 떠올리는 노력**(바람직한 어려움)이 기억을 만든다
- 모르는 게 나왔을 때 진도를 멈추는 게 맞다
- 시간이 모자라면 기능을 줄인다. 이해는 줄이지 않는다
