| 문제 | 토요일 | 오늘 |
|---|---|---|
| 서버 스레드가 자는 동안 C의 연결과 데이터는 누가, 어디에 보관하나 | 빈틈 | ⭕ |

| 스레드 풀의 Worker는 언제 잠드나 | 빈틈 | ⭕ |

**실험으로 직접 본 것은 이틀이 지나도 남아 있었다.**

오늘 다시 정리한 것:
- **서버 스레드가 자고 있어도 커널은 계속 일한다.** 연결은 커널 대기열에, 요청 데이터는 커널 안의 그 연결 전용 보관함에 있다.
- fd의 흐름:
  ```
  main이 accept()를 호출해서 커널에게 "연결 하나 줘"라고 요청
  → 커널이 accept()의 반환값으로 main에게 fd를 준다
  → main이 fd를 일감 대기열(서버 내부 배열)에 넣는다 (스레드 풀일 때. 커널은 ②를 모른다)
  ```

## 4. 실험 04: epoll ✅

### 구조
스레드는 **main 하나뿐**이다. main 하나가 연결 받기와 요청 처리를 전부 한다.

| 함수 | 하는 일 |
|---|---|
| `epoll_create1` | 커널 안에 **"지켜볼 fd 목록"**을 만든다. 목록 자체도 fd다 (그래서 첫 연결이 fd 4가 아니라 5를 받았다) |
| `epoll_ctl` | fd를 목록에 **하나씩** 등록하거나 해제한다 |
| `epoll_wait` | 목록 번호만 넣고 잠든다. 등록된 fd 중 **아무거나** 할 일이 생기면 깨어나고, **할 일이 생긴 fd들**을 돌려받는다 |

`read(fd)`와 비교하면:

| 함수 | 지켜보는 것 | 잠드는 조건 |
|---|---|---|
| `read(fd)` | fd **1개** | 그 fd에 데이터가 없으면 |
| `epoll_wait` | 등록된 fd **여러 개** | 등록된 fd **전부** 할 일이 없으면 |

- "잠든다" = 함수를 불렀는데 아직 끝나지 않은 상태
- 지켜보는 건 main이 아니라 **커널**이다. main은 자고 있다
- 목록에는 순서가 없다. 누가 먼저 데이터를 보낼지 예측할 수 없으니 정렬할 필요가 없다

이 서버에서 "할 일"은 두 종류뿐이다.

| 등록된 fd | 생기는 일 | main이 하는 것 |
|---|---|---|
| listen 소켓 | 새 연결이 옴 | accept → 새 fd를 목록에 등록 |
| 연결 fd | 요청 데이터가 옴 | read → write → close → 목록에서 해제 |

### 실험: 느린 클라이언트 2개(B1, B2) + C
```
[main] ⏰ listen fd에 새 연결 -> accept -> fd 5 생김, 등록 (지켜보는 연결 1개)   ← B1
[main] epoll_wait -> 잠듦💤 (지켜보는 연결 1개)                                    ← B1에 묶이지 않고 돌아옴
[main] ⏰ listen fd에 새 연결 -> accept -> fd 6 생김, 등록 (지켜보는 연결 2개)   ← B2
[main] ⏰ listen fd에 새 연결 -> accept -> fd 7 생김, 등록 (지켜보는 연결 3개)   ← C
[main] epoll_wait -> 잠듦💤 (지켜보는 연결 3개)
[main] ⏰ fd 7에 요청 데이터 도착                                                  ← 커널이 깨움
[main]   read(7) -> 77 바이트, 안 잠들고 바로 읽음
[main]   fd 7 응답 보내고 close (지켜보는 연결 2개)
```

- 실험 01에서는 B가 연결되자 main이 `read(B)`에서 꼼짝 못 했다. 이번엔 B1을 목록에 올려두고 **바로 epoll_wait로 돌아왔다.**
- **"커널이 지켜본다"가 보이는 순간:** main이 자고 있는 동안, 누군가 "B1, B2는 조용하고 fd 7에 데이터가 왔다"는 걸 알아채서 main을 깨웠다. 그게 커널이다.
- **없는 줄:** fd 5, 6에 대한 `요청 데이터 도착`이 없다. main은 B1, B2를 **한 번도 read하지 않았다.**

### 검증 스크립트
- 느린 클라이언트 2개 → **PASS ✅** (예측과 일치)
- 궁금해서 100개로 돌려봄 → **PASS ✅**. 스레드 1개로 느린 클라이언트 100개를 버텼다. 스레드 풀(Worker 2)은 2개에서 무너졌다.

### 내 말로 3줄
1. **본 것:** 느린 클라이언트의 read에 main 스레드가 묶이지 않았고, 그래서 마지막에 연결하고 요청한 C가 응답받았다.
2. **원인:** main은 등록된 느린 클라이언트 2개에게서 처리할 게 없어서 epoll_wait에서 잠들었고, 커널이 C의 요청 데이터 도착을 알려줬다.
3. **그래서:** epoll은 연결된 클라이언트가 실제로 요청했을 때만 반응한다. **스레드 풀은 스레드 하나가 클라이언트 1개를, epoll은 스레드 하나가 매우 많은 클라이언트(한계: fd 개수와 메모리)를 맡는다.**

## 5. 동시성 실험 4개 총정리: 본 것 / 원인 / 그래서

공통 실험: 느린 클라이언트(연결만 하고 요청을 안 보냄) N개 + C(요청을 바로 보냄). C가 2초 안에 응답받나?

| 실험 | 스레드 | 본 것 | 원인 (어디서 잠드나) | 그래서 (약점 → 다음 단계) |
|---|---|---|---|---|
| 01 단일 스레드 | main 1 | 느린 클라이언트 **1개**에도 C 멈춤 | main이 `read(B)`에서 잠듦 → accept로 못 돌아감 | 스레드 하나가 모든 일을 함 → **스레드를 늘리자** |
| 02 연결마다 스레드 | main + 연결 수만큼 | 느린 클라이언트가 있어도 C 응답 | 담당 스레드만 `read(B)`에서 잠듦, main은 accept 계속 | 클라이언트 1만 개 = 스레드 1만 개 → 메모리 → **스레드 수를 고정하자** |
| 03 스레드 풀 | main + Worker 2 | 1개 PASS, **2개 FAIL**. C는 연결은 됐지만 처리 안 됨 | Worker 2개가 모두 `read(B1)`, `read(B2)`에 묶임 → C의 fd는 일감 대기열에서 대기 | 스레드 하나 = 클라이언트 하나 → **read에 묶이지 않게 하자** |
| 04 epoll | main 1 | 2개, **100개**에도 PASS | main은 `epoll_wait`에서 잠듦. 커널이 데이터가 온 fd(C)만 알려줌 → 느린 클라이언트는 read 안 함 | 스레드 하나 = 클라이언트 매우 많이. 남은 것: 코어 1개만 씀 → **④ 하이브리드** |

### 성적표
| 서버 | 스레드 수 | 느린 클라이언트 1개 | 2개 | 100개 |
|---|---|---|---|---|
| 단일 스레드 | 1 | FAIL | FAIL | - |
| 연결마다 스레드 | 클라이언트 수만큼 | PASS | PASS | (스레드 100개) |
| 스레드 풀 | 1 + Worker 2 | PASS | **FAIL** | - |
| **epoll** | **1** | PASS | PASS | **PASS** |

**한 줄 요약:** 01~03의 공통 원인은 **"스레드가 클라이언트 하나의 `read`에 묶인다"**이고, epoll은 **"데이터가 온 fd만 read한다"**로 이걸 없앴다.
