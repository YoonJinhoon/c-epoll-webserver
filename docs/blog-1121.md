## 2. 검증: AI가 짠 코드를 나는 어떻게 믿나

### 출발점
> 오류가 있다는 건 검증할 수 있지만, 오류가 없다는 건 검증할 수 없다.

다익스트라도 같은 말을 했다. *"테스트는 버그가 **있다**는 걸 보여줄 수는 있지만, **없다**는 걸 보여줄 수는 없다."*
그래서 목표는 "오류 0 증명"이 아니라 **한정된 에너지로 큰 오류부터 최대한 찾기**다.

### 검증할 대상은 2개
| 대상 | 질문 |
|---|---|
| 결과물 (서버 코드) | 요구사항대로 **동작하나?** |
| 나의 이해 | 내가 **설명하고 다시 만들 수 있나?** |

### 모든 검증은 4칸으로 적는다
| 주장 (통과 기준) | 검증 방법 | 증거 | 판정자 |
|---|---|---|---|

1. 주장과 방법은 **실행 전에** 적는다. 결과를 보고 끼워 맞추지 않기 위해서다.
2. 증거는 **복붙할 수 있는 것만** 쓴다 (로그 줄, 출력, 숫자).
3. **판정자**를 적는다. AI가 판정한 건 아직 내 검증이 아니다.

### "맞는 결과"를 모를 때 기댈 곳
| 기준 | 예 |
|---|---|
| ① 과제 명세 | "404/403/500을 처리하라" |
| ② 검증된 다른 서버와 비교 | 같은 요청을 다른 서버에도 보내고 출력을 비교 |
| ③ 내 예측 | 실험 전에 적어둔 예측 |

### 전부 의심하지 않는다
**터지면 피해가 큰 곳부터** 의심한다. 서버가 죽는다, 메모리가 샌다, 한 클라이언트가 다른 모든 클라이언트를 막는다.
과제 원문을 33줄로 쪼개서 줄마다 피해 크기(🔴🟡⚪)를 붙였다. 그리고 "내가 아나?"를 솔직하게 찍었더니 **33줄 전부 △(들어봄)**였다. 이게 출발점이다.

## 3. 첫 검증 스크립트: `test_slow_client.sh`

### 무엇을 자동화하나
어제 터미널 3개로 손으로 하던 실험이다.

| 손으로 | 스크립트가 대신 |
|---|---|
| 터미널 A: 서버 켜기 | 서버 켜기 |
| 터미널 B: `nc` 연결만 하고 가만히 (느린 클라이언트) | nc 켜기 |
| 터미널 C: `curl` | curl 보내기 |
| 눈으로 C 화면 확인 | 판정 |

- **느린 클라이언트** = 서버에 연결만 하고 요청 데이터를 보내지 않는 클라이언트
- **`nc`** = netcat. 서버에 연결해서 키보드로 친 글자를 보내고, 받은 글자를 보여준다

### 통과 기준을 말로 정하기
처음 기준: *"B가 가만히 있을 때, C에 응답이 출력되면 통과."*
→ 구멍이 있다. 단일 스레드 서버도 B가 10분 뒤에 요청을 보내면 C가 결국 응답을 받는다.
→ 고친 기준: **"B가 가만히 있을 때, C가 2초 안에 응답을 받으면 PASS."**
(정상 응답은 약 0.01초, 막히면 무한이다. 2초면 충분히 구분된다.)

### 실행
```bash
bash tests/test_slow_client.sh <검사할 서버 실행 파일>
```
저장소 맨 위 폴더에서 실행한다. 경로가 맨 위 폴더 기준으로 적혀 있기 때문이다.

### 테스트가 거짓말을 했다
첫 실행에서 **단일 스레드 서버가 PASS**로 나왔다. 막히는 서버니까 FAIL이 나와야 한다.
원인: 실험 02 서버가 다른 터미널에서 **켜져 있었다.** 그래서 테스트가 띄운 서버는 포트를 못 잡고 죽었고, curl은 **켜져 있던 엉뚱한 서버**에게 응답을 받았다.

고친 것 (안전장치 = "테스트가 엉뚱한 걸 검사하고 있지 않은가"를 검사하는 장치):
- 포트가 이미 사용 중이면 → **중단** (가짜 PASS 방지)
- 테스트가 켠 서버가 바로 죽으면 → **중단** (가짜 FAIL 방지)

결과가 PASS / FAIL / **중단(판정 불가)** 3가지가 됐다.

### 스크립트 자체를 검증
| 서버 | 기대 | 결과 |
|---|---|---|
| 단일 스레드 | FAIL | FAIL ❌ |
| 연결마다 스레드 | PASS | PASS ✅ |

**한 번도 실패하지 않는 테스트는 믿으면 안 된다.** 막히는 서버에서 FAIL이 나오는 걸 확인해야 이 테스트를 믿을 수 있다.

## 4. 실험 03: 스레드 풀 ✅

### 구조
Worker 스레드를 **처음에 2개만** 만들어 두고 재사용한다. 서버 안에 스레드는 3개(main, W1, W2)다.

| 스레드 | 하는 일 |
|---|---|
| main | **연결 받기만** (accept → ②에 fd 넣기) |
| Worker | **요청 처리 전부** (②에서 fd 꺼내기 → read → 응답 만들기 → write → close → 다시 ②로) |

### 대기열 2개
| | 어디에 있나 | 들어 있는 것 |
|---|---|---|
| ① 커널 대기열 | **커널 안** | 아직 accept되지 않은 연결 (fd는 아직 없다) |
| ② 일감 대기열 | **서버 프로그램 안** (우리가 만든 배열) | Worker를 기다리는 fd 번호 |

- 연결은 **커널 → main → Worker** 순서로 넘어간다. main이 accept할 때부터 fd 번호로 불린다.
- 요청 데이터는 ②에 들어가지 않는다. **Worker가 `read`할 때까지 커널 안에** 있다.
- fd는 서버 프로그램이 그 연결을 부르는 번호일 뿐이다. 클라이언트 쪽은 같은 연결을 자기만의 번호로 부른다.
- close = 연결을 끊고 fd 번호를 반납한다. 반납된 번호는 재사용된다.

### 스레드가 잠들고 깨는 조건
| 스레드 | 잠드는 조건 | 깨어나는 조건 |
|---|---|---|
| main | ①이 비었을 때 (`accept`) | ①에 새 연결이 생기면 |
| Worker | ②가 비었을 때 | ②에 fd가 생기면 |
| Worker | `read` 후 요청이 안 왔을 때 | 그 클라이언트가 요청을 보내면 |

### 실험: Worker 2개 + 느린 클라이언트 2개(B1, B2) + C

| 단계 | 로그 | 예측 |
|---|---|---|
| 서버 시작 | main은 accept💤, W1·W2는 ②💤 (스레드 3개 모두 잠듦) | |
| B1 연결 | main⏰ fd 4 → ② → W1⏰ → `read(4)`💤 | "main이 깨고 다시 잠든다" ✅ |
| B2 연결 | fd 5 → W2 → `read(5)`💤 | "W2가 깬다" ✅ |
| C 연결 | **`[main] ⏰ ①에서 연결 꺼냄 -> fd 6 생김`** | "C는 연결될 여지가 없다" ❌ |
| B1이 요청 보냄 | W1이 B1 처리 → close → **②에서 fd 6을 꺼내 C 처리** | "W2가 아니라 W1이 꺼낸다" ✅ |

### 가장 중요한 발견: 연결과 처리는 다른 단계다
C 연결 직후 로그에 `fd 6 생김`은 **있고**, `②에서 fd 6 꺼냄`은 **없었다.** 없는 줄도 증거다.

> **C는 연결은 됐지만 처리는 안 됐다. 왜냐하면 처리해줄 Worker 스레드가 없기 때문이다.**

| | 누가 | C의 상태 |
|---|---|---|
| 연결 | main (accept) | ✅ 됨 |
| 처리 | Worker (read → write → close) | ❌ ②에서 대기 |

연결은 스레드가 아니라 **클라이언트 프로그램과 서버 프로그램**이 맺는다.

B1과 C는 둘 다 막혔지만 이유가 다르다.

| | Worker가 맡았나 | 막힌 이유 |
|---|---|---|
| B1 | ✅ W1 | B1이 요청을 안 보내서 W1이 `read`에서 기다림 |
| C | ❌ | 요청은 이미 보냈지만 놀고 있는 Worker가 없음 |

### 로그로 Worker 5단계를 두 바퀴 따라가기
```
[W1] ⏰ read(4) 깨어남 -> 14 바이트          → 2 (read)
[W1] fd 4 응답 보내고 close -> 다시 ②로      → 3, 4, 5, 1
[W1] ②에서 fd 6 꺼냄                        → 1
[W1] read(6) -> 잠듦💤                       → 2
[W1] ⏰ read(6) 깨어남 -> 77 바이트           → 2
[W1] fd 6 응답 보내고 close -> 다시 ②로      → 3, 4, 5, 1
[W1] ②가 비어 있음 -> 잠듦💤                 → 1
```
로그 한 줄에 여러 단계가 들어 있을 수 있다.

**로그도 거짓말을 한다.** `read(6) -> 잠듦💤` 바로 다음 줄이 `깨어남`이다. 실제로는 잠들지 않았다. C의 요청이 이미 커널에 와 있었기 때문이다. 로그는 read를 부르기 **직전에** 찍혔을 뿐이다. 로그도 코드가 쓴 문장이라 앞뒤 줄과 맞춰봐야 한다.

### 스레드 풀의 약점
> 스레드 풀의 **모든 Worker가 느린 클라이언트의 `read`에 묶이면**, 다른 클라이언트의 요청은 처리되지 않는다.

("모든 스레드가 잠들면"은 틀린 표현이다. 서버 시작 때도 스레드는 모두 잠들어 있었지만 문제가 없었다. 문제는 **어디서** 자느냐다.)

### 검증 스크립트로도 확인
예측: Worker 2개, 느린 클라이언트 1개 → **PASS** (W1이 느린 클라이언트를, W2가 C를 맡으니까) → **PASS ✅ 일치**

하지만 이 PASS가 **증명하지 못하는 것**이 있다. 스크립트는 느린 클라이언트를 1개만 붙인다. 그래서 "느린 클라이언트가 Worker 수만큼 오면 막힌다"는 약점을 **잡지 못한다.**
PASS는 "이 상황에서는 괜찮다"일 뿐이다.

## 6. 오늘 배운 학습 방법
- **보고 알아보기 ≠ 꺼내기.** 정리를 정독하면 "안다"는 느낌이 들지만, 백지에서 꺼내는 건 다른 일이다.
- **표로 읽으면 막히고, 로그로 보면 풀린다.** 대기열은 표로 3번 설명을 들어도 막막했는데, 로그로 한 번 보니 설명할 수 있게 됐다.
- **오래 쓰는 기법 3가지:** 의도적 연습(예측 → 실험 → 즉시 판정), 인출 연습(빈틈 체크), 파인만 기법(백지에 내 말로 3줄)
