# 웹 서버 5일차: timeout (11/25)

## 1. epoll_wait가 깨어나는 걸 눈으로 보기
`epoll_wait(..., -1)` → `1000`으로 바꾸고, 바로 다음 줄에 `printf("[main] 깼음 n=%d\n", n);`

```
[main] 깼음 n=0                              ← 1초 동안 아무 일 없음
[main] 깼음 n=1                              ← ① 새 연결 (할 일 A)
[fd 5] 연결됨 -> 보관함 만들고 등록
[main] 깼음 n=1                              ← ② 요청 데이터 (할 일 B)
[fd 5] 조각 77 바이트 도착 -> 보관함 77 바이트
...
[main] 깼음 n=0                              ← 다시 1초마다
```

### 내 4줄 채점
1. **"n은 fd 목록에 저장된 fd의 개수?"** ❌ → **이번에 할 일이 생긴 fd의 개수.** 근거: curl이 오기 전 목록에는 listen fd 1개가 있었는데 `n=0`. ②에서는 목록에 2개(listen, fd 5)가 있었는데 `n=1`
2. **"둘 다 바로 아래 줄의 로그가 근거"** ✅
3. **"①: 커널로부터 fd 5를 받은 연결"** ✅ 할 일 A. 단, ①에서 epoll이 알려준 fd는 fd 5가 아니라 **listen fd**("새 연결 왔음"). fd 5는 깨어난 **다음에** `accept`가 받아온 번호 ← 내가 놓친 섬세한 부분
4. **"②: 해당 연결이 요청 데이터를 보냄"** ✅ 할 일 B. 이때 epoll이 알려준 fd가 fd 5

### -1과 1000
- `-1` = "영원히"가 아니라 **할 일이 생길 때까지 무한정**. 어제 1,019개가 가만히 있어서 영원히 안 깨어난 것처럼 보였다
- `1000` = "1초 잔다"가 아니라 **최대 1초**. 그 사이에 curl이 오면 바로 깬다
- `events`가 복수형인 이유: 한 번 깰 때 할 일이 n개일 수 있다 (배열 최대 64칸)

### 함정: make 했는데 printf가 안 찍힘
`make`할 때 `printf` 줄이 아직 저장 안 된 상태였다 → 옛날 코드로 컴파일. 11/23의 "옛날 ./webserver를 검사함"과 같은 종류. **실행 파일이 내가 보는 코드와 같은가?**

## 2. timeout: 1초마다 모든 보관함 훑기
- 보관함에 `last_active` = 마지막으로 무언가 도착한 시각. 갱신은 두 번: **연결된 순간**(`conn_open`) + **바이트가 도착할 때마다**(`conn_on_data`, 머리든 본문이든)
- main 루프에서 `epoll_wait` 처리 **다음에** `conns[0]`~`conns[1023]`을 하나씩 본다. 빈 칸은 건너뛰고, 연결이 있으면 오래 조용했는지 검사
- `epoll_wait`가 최대 1초마다 깨니까, 그 다음 줄의 훑기도 **1초마다** 실행된다 (`깼음 n=0`이 1초마다 찍힌 것과 같은 원리)

### 내가 쓴 조건 (두 번 만에)
- 1차: `IDLE_TIMEOUT >= now - c->last_active` → 반대 (방금 연결된 것: 5 >= 0 참 → 바로 닫힘, 6초 조용한 것: 5 >= 6 거짓 → 안 닫힘)
- 2차: `IDLE_TIMEOUT <= now - c->last_active` → 5초 이상 조용하면 닫는다

### 연결 칸이 1,019자리인 이유 (표로)
`conns` 표는 칸 1,024개, **칸 번호 = fd 번호**. 앞 다섯 칸은 서버가 이미 쓴다.

| fd 번호 | 누가 쓰나 | 클라이언트가 받을 수 있나 |
|---|---|---|
| 0 | 표준 입력 (모든 프로세스) | ❌ |
| 1 | 표준 출력 (모든 프로세스) | ❌ |
| 2 | 표준 에러 (모든 프로세스) | ❌ |
| 3 | listen 소켓 (우리 서버가 첫 번째로 엶) | ❌ |
| 4 | epoll 목록 (우리 서버가 두 번째로 엶) | ❌ |
| **5 ~ 1023** | **클라이언트 연결** | ✅ **1,019개** (1023 − 5 + 1) |
| 1024 이상 | `conn_open`이 `fd >= MAX_FDS`라서 바로 close | ❌ |

어제(11/24) 로그의 `연결됨` 1019가 이 계산과 정확히 맞았다.

### timeout 줄 수 예측 (1019) — 클라이언트별로 따라가기
`grep -c timeout` = `timeout` 글자가 든 줄 수. 그 줄은 훑기 안 `printf` 한 곳에서만 찍힌다. 훑기는 `conns` 표에 **보관함이 있는 칸만** 검사 → "표에 들어간 적 있고 + 5초 조용했던 연결"만 찍힌다.

| 누가 | 몇 개 | 무슨 일이 생기나 | 찍히는 로그 | `timeout` 줄 |
|---|---|---|---|---|
| 먼저 온 nc | 1,019 | fd 5~1023을 받아 표에 들어감 → 아무것도 안 보냄 → 5초 뒤 훑기에 걸림 | `연결됨` → `timeout` | 1,019 |
| 나중에 온 nc | 81 | fd 1024 → `conn_open`에서 표에 안 넣고 바로 close | `꽉 참` | 0 |
| 붙인 직후 curl | 1 | 자리가 없어서 바로 close | `꽉 참` | 0 |
| 10초 뒤 curl | 1 | 빈자리 받음 → 요청 → 200 → 닫음 (5초 전에 끝남) | `연결됨` → `200` → `close` | 0 |
| 합계 | | | | **1,019** |

## 4. S6 timeout 정리 (내 3줄 + 바로잡은 것)
1. **본 것:** 느린 클라이언트 1,100개를 붙이자 (그중 자리를 받은 건 1,019개), 붙인 직후 curl은 실패, 40초 뒤 curl은 성공. timeout으로 닫힌 연결은 1,019개
   - 바로잡음: 처음엔 "1019개를 붙이자"라고 씀 → 붙인 건 1,100, 자리 받은 게 1,019
2. **방법:** `epoll_wait`의 마지막 인자를 `-1` → `1000`(ms)으로 바꾸면 할 일이 없어도 최대 1초마다 깨어난다. 깨어난 다음 줄에서 모든 보관함을 훑으며 `지금 시각 − last_active`가 30초 이상이면 닫는다
   - `last_active` = **마지막 요청 데이터 조각이 서버에 도착한 시각** (클라이언트가 보낸 시각 ❌ — 서버는 도착만 안다). 그리고 **연결된 순간**에도 기록한다
3. **그래서:** 아래 표

### 이걸 막았고, 이건 아직 못 막는다
| | 공격 방식 | 지금 timeout (마지막 도착 후 30초) | 이유 |
|---|---|---|---|
| ✅ 막음 | 연결만 하고 **아무것도 안 보냄** | 30초 뒤 닫힘 | `last_active`가 연결 순간에 멈춰 있음 → 조용한 시간이 30에 닿음 |
| ❌ 못 막음 | **29초마다 1바이트씩** 보냄 (진짜 Slowloris) | 영원히 안 닫힘 | 1바이트가 올 때마다 `last_active`가 그 시각으로 갱신 → 조용한 시간이 0으로 돌아감 |

29초마다 1바이트 따라가기:
| 시각 | 일어난 일 | last_active | 조용한 시간 | 닫히나 |
|---|---|---|---|---|
| 100 | 연결 | 100 | 0 | ❌ |
| 129 | 1바이트 | 129 | 0으로 돌아감 | ❌ |
| 158 | 1바이트 | 158 | 0으로 돌아감 | ❌ |
| … | 반복 | | 30에 영원히 못 닿음 | 영원히 안 닫힘 |

막으려면: "**연결된 순간부터 요청 전체를 30초 안에**" (전체 마감) 같은 규칙. 단, 이것도 느린 네트워크에서 큰 파일을 정직하게 올리는 사용자를 자른다 → 실제 서버는 둘을 같이 쓰거나 "초당 최소 몇 바이트" 규칙을 쓴다.

왜 처음부터 전체 마감으로 안 했나: S4에서 찾은 문제가 "아무것도 안 보내고 영원히 붙어 있음"이었고, 그걸 막는 가장 단순한 방법(필드 하나)이 idle timeout이었다. 조금씩 보내는 공격은 그다음에 알게 됐다.

### 점심 뒤에 읽을 것: 왜 "모든 보관함"을 훑나
- epoll이 알려주는 것: 할 일이 **생긴** fd (`events`, n개)
- timeout이 알아야 하는 것: 30초 동안 할 일이 **없었던** fd
- 조용한 연결은 할 일이 없으니 **`events`에 절대 안 나온다** → epoll은 "누가 조용한지" 모른다 → 서버가 직접 `conns[0]`~`conns[1023]`을 한 칸씩 열어 시각을 확인
- 질문: timeout 검사를 `for (i < n)` 안에서(= `events`에 나온 fd만) 하면 어떻게 되나?

### (점심 뒤) 훑기 이해 ✅
- 30초 실험 때 화면이 `[main] 깼음 n=0`으로 꽉 찼다 → 느린 클라이언트 1,019개가 붙어 있는데도 **n=0 = events가 비어 있음**
- main 루프 안 반복문은 두 개: ① `for (i < n)` events 처리 → n=0이면 **0번** (`0 < 0` 거짓) / ② `for (fd < 1024)` 훑기 → 항상 1,024번
- 처음엔 ①이 몇 번 도냐는 질문에 "1024번" → 반복문 둘을 헷갈림
- 내 답: timeout 검사를 ① 안에 넣으면 **안 닫힌다. events에 한 번도 안 나오니까** ✅

## 5. S5 Reverse Proxy (오후)

### 왜 넘기나 (처음에 이걸 몰라서 1시간 헤맴)
- 웹사이트 요청은 2종류: **정적**(파일, 우리 서버가 디스크에서 읽어 응답) / **동적**(로그인·목록처럼 계산이 필요, **다른 프로그램(백엔드)**이 처리)
- 서버가 둘을 구분할 수 있는 단서 = 요청 라인의 경로 → **우리가 정한 규칙**: `/api/`로 시작하면 동적 → 8001 백엔드로 넘김
- 내 조건: `if ( strncmp(rl.path, "/api/", 5) == 0 )` (따옴표 깜빡 → VSCode 자동완성으로 깨달음)
- 우리 서버는 **curl에게는 서버, 백엔드에게는 클라이언트**

### 결과
| 실험 | 결과 | 증거 |
|---|---|---|
| b. 백엔드 켜짐 | `8001 백엔드가 처리함` | 헤더 `Server: SimpleHTTP Python`, `HTTP/1.0` → 백엔드가 만든 응답을 손대지 않고 전달 |
| c. 백엔드 꺼짐 | `502 Bad Gateway` | 로그 `연결 실패 -> 502`. 내 예측 "응답 없음" ❌ → 502 코드가 없었다면 그렇게 됐을 것 |
| d. 대답 안 하는 백엔드(`nc -l 8001`) + 다른 클라이언트가 `/index.html` | D: `(28) timed out ... 0 bytes` | A 로그에 `[fd 7] 연결됨` 줄이 **없음** → accept조차 못 함 |

- 502 = 프록시가 백엔드에게서 응답을 제대로 받지 못했다
- 그림: https://claude.ai/artifact/A26fv9Z4QMswBMiLhJFjMh

### d가 왜 멈췄나
- `proxy_to_backend`의 `read(fd 6)`이 응답(또는 닫힘)이 올 때까지 **블로킹** → 스레드 1개가 `epoll_wait`로 못 돌아감 → D의 연결을 accept 못 함 → 백엔드와 상관없는 요청까지 전부 멈춤
- 실험 01(단일 스레드)과 같은 증상. epoll을 써도 **epoll을 거치지 않은 read 하나**가 서버 전체를 멈춘다
- 하이브리드(스레드 여러 개)는 피해를 줄일 뿐 근본 해결 아님. 근본 해결 = fd 6도 epoll에 등록 (nginx 방식, 대신 fd 5와 fd 6의 짝·진행 상태를 기억해야 해서 복잡)

### 정독할 때 다시 생각할 것 (내가 고른 3개)
```
fd 6(백엔드 쪽)에서는 역할이 뒤집힙니다. write로 요청을 보내고, read로 응답을 읽습니다. 우리 서버가 백엔드에게는 클라이언트이기 때문입니다.

epoll은 "이 fd에 데이터가 이미 와 있다"고 알려 줍니다. 그 fd를 read하면 데이터가 이미 있으니 바로 끝나고, 블로킹되지 않습니다.
등록하지 않은 fd를 그냥 read하면, 데이터가 올 때까지 블로킹될 수 있습니다.

기다려야 할 가능성이 있는 fd 는 전부 등록한다.
```
| 등록 위치 | fd | 이유 |
|---|---|---|
| main.c:351 | listen fd (3) | 새 연결이 언제 올지 모름 |
| main.c:59 `conn_open` | curl 쪽 fd (5, 7, …) | 요청이 언제 올지 모름 |
| (없음) | 백엔드 쪽 fd (6) | 응답이 언제 올지 모르는데 등록 안 함 → 이번 버그 |

### d 뒤: nc를 Ctrl+C로 끄자
```
[fd 5] 연결됨 -> 보관함 만들고 등록
[fd 5] 조각 87 바이트 도착 -> 보관함 87 바이트
[fd 5] 파싱 성공: method=GET path=/index.html
[fd 5] 파일 www/index.html (141 바이트) 보냄 -> 200
```
- 백엔드가 연결을 닫음 → `read(fd 6)`이 0을 돌려주며 **깨어남** → 스레드가 `epoll_wait`로 돌아감 → 커널 대기열에 있던 **D의 연결을 그제야 accept**
- D의 번호가 7이 아니라 **5**: 그때는 C(fd 5)와 백엔드(fd 6)가 이미 닫혀서, 커널이 비어 있는 가장 작은 번호 5를 줌
- 87바이트 = `/index.html` 요청 (`/api/hello` 86바이트보다 경로가 1글자 길다)
- 그런데 D는 5초 만에 이미 포기했다 → 서버는 **떠난 클라이언트에게** 200을 보낸 셈

| ⑤ | **예측과 비교**: 내 예측과 다른 곳은? 어떤 재료가 틀렸나? | 내 머릿속 모델의 구멍 | "D는 받는다" ❌ → 재료 "스레드는 1개, read는 블로킹" 빠짐 |

## 7. 새 연결이 생기는 사슬 (자꾸 까먹는 것)
| 단계 | 누가 | 하는 일 | 로그 |
|---|---|---|---|
| 1 | 클라이언트 | `connect` (curl이 9100에 접속) | (없음) |
| 2 | 커널 | 연결을 완성해서 listen fd의 **대기열**에 넣어 둠 | (없음) |
| 3 | 우리 서버 | `epoll_wait`가 깨어남: "listen fd(3)에 할 일 있음" | (없음) |
| 4 | 우리 서버 | `accept` 호출 → 커널이 대기열에서 꺼내 **새 fd**(가장 작은 빈 번호)를 줌 | (없음) |
| 5 | 우리 서버 | `conn_open`: 보관함 만들고 새 fd를 epoll에 등록 | `[fd 5] 연결됨 -> 보관함 만들고 등록` |
| 6 | 우리 서버 | 다음 `epoll_wait`에서 "fd 5에 할 일 있음" → `read` | `[fd 5] 조각 86 바이트 도착` |

- S5-d에서 D가 멈춘 곳 = **2단계** (대기열에 들어갔지만 서버가 3단계로 못 감)
- S6에서 fd 1024가 닫힌 곳 = **5단계** (`conn_open`이 1024 이상이면 바로 close)

## 8. 힘듦에는 두 종류가 있다
| 좋은 힘듦 (실력이 늚) → 견딘다 | 나쁜 힘듦 (실력과 무관) → 없앤다 |
|---|---|
| 보지 않고 떠올리기 (accept 사슬 빈칸 쓰기) | 설명이 빠져서 이해가 안 됨 (오후 프록시: "왜" 없이 "어떻게"부터) |
| 예측했는데 틀림 ("D는 받는다" ❌) | 도구가 헷갈림 (fish 셸, 엉뚱한 로그 파일) |
| 빈칸 채우기 (timeout 조건, `/api/` 조건) | 소음, 피로 |

- 오른쪽을 느끼면 바로 말한다 (대부분 설명하는 쪽 몫)
- 관찰·규칙·추론·검증을 한꺼번에 잘하려 하지 말고, **로그 하나에 질문 5개**를 반복

## 9. accept 사슬 (내가 쓴 것, 고친 것)
1. curl 클라이언트가 9100 포트에 접속한다 ✅
2. 커널이 연결을 **listen 소켓의 대기열**에 넣어 둔다 ✅ (소켓의 실체는 전부 커널 안, 우리 프로그램은 번호 fd만 쥔다)
3. `epoll_wait`가 events에 listen fd를 담아 돌아오고, 그래서 main 스레드가 깨어난다 (처음엔 "main 스레드가 알려준다" → 주어 반대)
   - `epoll_wait`는 main 스레드가 **호출하는 함수**. 스레드가 그 안에 들어가 커널에서 잠들고, 커널이 깨우면 돌아 나온다
   - `read(fd 6)` 블로킹과 같은 모양. 차이: read는 fd **하나**, epoll_wait는 등록된 fd **전부**를 기다린다
4. 우리 서버가 `accept()`를 호출하면, 커널이 새 fd(가장 작은 빈 번호)를 준다 ✅
5. `conn_open`이 그 번호를 epoll 감시 목록에 등록한다 ✅

`conn_open`(우리 함수) 안에서 `epoll_ctl`(커널 함수, 시스템 콜)을 부른다. conn_open이 하는 일:
꽉 찼으면 close → 보관함 만들기(실패하면 close) → 보관함에 fd·지금 시각 적고 `conns[fd]` 표에 꽂기 → `epoll_ctl`로 감시 목록 등록 → 로그 `연결됨`
