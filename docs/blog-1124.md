## 1. 아침: 카드 꺼내기 (블로그 읽기 전에)

| 카드 | 결과 | 바로잡은 것 |
|---|---|---|
| fd 흐름 | △ | fd는 **연결될 때**(main이 accept할 때) 커널이 **main에게** 준다. 데이터가 올 때가 아니다. 그다음 main이 일감 대기열에 넣고, **놀고 있는 아무 Worker**가 꺼낸다 (미리 정해진 Worker는 없다) |
| epoll_wait | △ | "기다리는 함수"는 흐린 말. **등록된 fd들 중 할 일이 생길 때까지 main을 재우고, 생기면 그 fd들을 알려주는 함수** |
| 400/501/200 | ⭕ | 400 = **요청 라인**의 규칙 위반 / 501 = **모양은 맞지만** GET/POST가 아닌 메서드 |
| 서버 흐름 4단계 | ❌ | 스레드 풀(실험 03)과 섞였다. **일감 대기열 = 스레드 풀 / 보관함 = 진짜 서버(`src/`, epoll)** |

```
main이 accept 호출 → 커널이 fd를 main에게 줌 → main이 일감 대기열에 넣음 → 유휴 Worker가 꺼냄   (스레드 풀)
```
```
진짜 서버(epoll) 흐름
1. 연결이 오면 → 그 연결의 보관함을 만든다
2. 조각이 오면 → 보관함 끝에 붙이고 "머리가 다 왔나?" (아직이면 기다림)
3. 머리가 다 오면 → 요청 라인을 3조각으로 쪼갠다 (400 / 501 / 200)
4. 응답을 보내고 → 연결을 닫고 보관함을 버린다
```
생각보다 간단한데 자꾸 까먹는다. 그래서 간격을 두고 다시 꺼낸다.

블로그를 정독하면서 새로 찾은 빈틈:
- epoll 함수 3개: `epoll_create1`(지켜볼 fd 목록 만들기, 목록도 fd) / `epoll_ctl`(하나씩 등록·해제) / `epoll_wait`(목록 번호만 넣고 잠듦, 할 일이 생긴 fd들을 돌려받음)
- **(epoll) 조각이 덜 왔을 때 main이 그 연결을 기다리며 잠들면 안 된다.** 보관함에 넣어두고 epoll_wait로 돌아가 다른 연결을 처리한다

## 2. S3-a: 파일 보내기와 404

- **정적 파일** = 미리 만든 파일을 그대로 보냄. **동적 응답** = 요청마다 서버가 계산해서 만듦
- **루트 디렉토리** = 정적 파일을 모아둔 폴더(`www`). 서버를 켤 때 인자로 준다: `./webserver 9000 www`
- 서버는 **루트 폴더 뒤에 경로를 붙여서** 실제 파일을 찾는다: `www` + `/index.html` = `www/index.html`
- 없으면 **404**. 클라이언트는 `/nothing.html`을 적어 보냈지만, 서버가 확인해보니 없었다. **경로는 클라이언트가 적어 보낸 글자일 뿐이다.** 4xx = 클라이언트 잘못

### 응답 구조 읽기 (`curl -i`)
```
HTTP/1.1 404 Not Found         ← 상태 줄 (응답의 첫 줄, 상태 코드가 있는 줄)
Content-Type: text/plain       ┐
Content-Length: 10             ├ 헤더 ("이름: 값")
Connection: close              ┘
                               ← 빈 줄
not found                      ← 본문
```
- **응답에는 항상 상태 코드가 있다.** 본문이 비었다고 클라이언트가 "없다"는 걸 알 수는 없다
- `-i` = **include**. 없으면 curl은 본문만 보여준다
- `Content-Length: 10` = `not found` 9글자 + 줄바꿈 1개

### 서버 로그
```
[fd 5] 파싱 성공: method=GET path=/nothing.html
[fd 5] 파일 www/nothing.html 없음 -> 404
```

`serve_file` = **serve(내주다) + file**. "서버(server)"도 serve에서 온 말이다.
> GET 요청일 때 `serve_file`을 호출한다. www 뒤에 경로를 붙여 파일을 찾고, 있으면 200, 없으면 404.

## 3. S3-c: 서버를 직접 뚫고, 직접 막기

### 의심
`serve_file`은 `www` + 경로를 그대로 이어 붙인다. 클라이언트가 `GET /../src/main.c`를 보내면?
```
www/../src/main.c   →   www에서 한 칸 위(..)로 → src/main.c
```
**서버의 소스 코드**가 열린다. `..`을 여러 번 쓰면 컴퓨터의 아무 파일이나 읽어갈 수 있다. 이걸 **경로 탈출(path traversal)**이라고 한다.

### 직접 뚫어보기
```bash
curl --path-as-is localhost:9000/../src/main.c
```
`--path-as-is` = 경로를 적은 그대로 보내라 (curl은 원래 `..`을 미리 지워서 보낸다. 공격자는 그런 친절을 안 쓴다).
예측: main.c 내용이 나온다 → **실제로 나왔다.**

### 통과 기준 (바로잡은 것)
처음 쓴 기준: "4xx가 오고, main.c의 내용은 **출력되면** 통과" → **반대다.** 출력되면 뚫린 것이니 실패다. 한 단어가 뒤집히면 테스트가 보안 버그를 PASS로 만든다.
> `GET /../src/main.c` → **403**, main.c 내용은 **나오지 않으면** 통과

(403 = Forbidden, 금지. 숫자는 약속이라 처음엔 모를 수 있다. "4xx = 클라이언트 잘못"이라는 추론이 핵심)

### 막는 방법
`path_is_safe`: **파일을 찾기 전에**, 경로 조각 중에 `..`이 하나라도 있으면 403.
- 새 테스트가 **고치기 전 코드에서 FAIL**하는 걸 먼저 확인했다 (한 번도 실패 안 하는 테스트는 믿으면 안 된다)
- 직접 다시 켜서 확인: `HTTP/1.1 403 Forbidden`, 소스 코드 안 나옴
- 주의: 터미널에서 **돌고 있던 서버는 옛날 코드**였다. 고치면 다시 빌드하고 다시 켜야 한다

### 설계 선택
`/img/../index.html`은 결국 `www/index.html`이라 밖으로 안 나가지만, 지금 서버는 `..`이 있다는 이유만으로 403을 준다.

| 선택 | 장점 | 단점 |
|---|---|---|
| `..`이 있으면 무조건 막기 (지금) | 단순, 실수로 뚫릴 일 없음 | 안전한 경로도 막음 |
| `..`을 계산해서 진짜 밖으로 나가는지 확인 | 안전한 경로 통과 | 계산을 잘못하면 뚫림 |

**바로잡은 것:** "크롬 방식과 달리 예외 없이 막는다"가 아니다. **크롬은 `..`을 미리 정리해서 보내기 때문에 정상 사용자는 막히지 않는다.** 막히는 건 `..`을 그대로 보내는 이상한 클라이언트나 공격자뿐이다.

## 4. S3-b: MIME 타입 (직접 작성)

### 먼저 눈으로 보기
크롬에서 `http://localhost:9000/index.html`을 열었더니 웹페이지가 아니라 **HTML 코드 글자**가 그대로 보였다. 서버가 `Content-Type: text/plain`("그냥 글자다")을 보냈으니 크롬은 시키는 대로 글자로 보여준 것이다.

### MIME 타입
- **MIME** = Multipurpose Internet Mail Extensions. 원래 이메일 첨부파일용 규칙을 HTTP가 가져다 씀
- MIME 타입 = **`대분류/소분류`**. `/`는 경로가 아니라 **칸막이**. 소분류는 확장자와 가장 가까운 정보

| MIME 타입 | 뜻 |
|---|---|
| `text/html` | 글자 / html |
| `image/png` | 그림 / png |
| `application/octet-stream` | 프로그램용 데이터 / "그냥 바이트 덩어리" (octet = 8비트 = 바이트, stream = 흐름) |

- 크롬은 `octet-stream`을 받으면 **화면에 그리지 않고 다운로드만** 한다. 모르는 걸 화면에 그리는 게 더 위험하다 (숨은 코드가 실행될 수 있다). 다운로드는 저장만 하고 실행은 안 한다
- **기본값** = 해당하는 게 하나도 없을 때 쓰는 값

### 내가 쓴 코드
```c
const char *mime_type(const char *filename)
{
    const char *dot = strrchr(filename, '.');   /* 마지막 '.' 의 위치 */
    if (dot == NULL)
        return "application/octet-stream";

    if (strcmp(dot, ".html") == 0)
        return "text/html";
    if (strcmp(dot, ".css") == 0)
        return "text/css";
    if (strcmp(dot, ".js") == 0)
        return "text/javascript";
    if (strcmp(dot, ".png") == 0)
        return "image/png";
    if (strcmp(dot, ".jpg") == 0 || strcmp(dot, ".jpeg") == 0)   /* .jpeg 는 내가 추가 */
        return "image/jpeg";

    return "application/octet-stream";          /* 기본값 */
}
```
- `strcmp` = **str**ing **c**o**mp**are. `strrchr` = **str**ing **r**everse **chr**. 글자를 **뒤에서부터** 찾는다
- **왜 뒤에서부터?** `my.page.html`처럼 점이 여러 개일 수 있다. 마지막 점 뒤가 진짜 확장자다
- 함수 모양 (바로잡은 것): 넣는 건 확장자가 아니라 **파일 이름 전체**, 돌려주는 건 `Content-Type: text/html`이 아니라 **값(`text/html`)만**. `Content-Type: ` 부분은 main.c가 붙인다. **key는 main.c가, value는 mime_type이**

### 결과
- 예측: "It works! 글자만 나올 것" → 크롬에 **큰 굵은 글씨 It works!** (굵기는 예상 못 함. `<h1>` = 큰 제목. `text/plain`일 땐 `<h1>`을 글자 그대로, `text/html`일 땐 명령으로 알아듣고 그림)
- 같은 141바이트인데 **헤더 한 줄**이 결과를 바꿨다

### 단위 테스트 9개 (내가 직접 돌림)
| 줄 | 검사하는 것 |
|---|---|
| index.html ~ a.jpg (5줄) | 내가 쓴 5개 확장자 |
| a.jpeg | 내가 추가한 `\|\|` |
| my.page.html | 마지막 점을 보는가 (`strchr`로 앞에서 찾았다면 이 줄이 FAIL) |
| README, a.zip | 확장자가 없거나 모를 때 기본값 |

이 파일들은 `www`에 실제로 없다. 단위 테스트는 파일을 열지 않고 **이름 → MIME 타입** 함수만 검사한다.

### 내 코드의 약점
`INDEX.HTML`, `photo.PNG` 같은 **대문자 확장자**: `strcmp(".HTML", ".html")`은 다르다고 나온다 → 기본값 → 크롬이 화면에 안 보여주고 **다운로드 폴더에 저장**해버린다. (바로잡은 것: 4xx가 아니다. 파일이 있으니 200이다. 문제는 Content-Type)

## 5. 크롬이 연결을 2개 연 이유
```
[fd 6] 파싱 성공: method=GET path=/index.html     ← 웹페이지
[fd 5] 파싱 성공: method=GET path=/favicon.ico    ← 탭 아이콘
```
우리 서버는 응답마다 연결을 닫는다(`Connection: close`). 요청이 2개면 연결도 2개 필요하다. 크롬은 빨리 보여주려고 **미리 2개를 열어두고**, 하나는 나중을 위해 남겨둔다. fd 5가 먼저 연결됐는데도 서버가 멈추지 않고 fd 6을 먼저 처리한 이유: **커널이 데이터가 온 fd 6만 epoll_wait로 알려줬기 때문**.

## 6. S3 정리: 내 3줄 + 바로잡은 것

1. **본 것:** 없는 파일 → 404 / 확장자에 맞는 Content-Type으로 응답 / 경로에 `..` → 403
2. **방법:** `mime_type`은 파일 이름을 받아서 뒤에서부터 처음 나오는 점부터를 확장자로 보고 strcmp로 비교해 MIME 글자를 return한다
   - 바로잡은 것: **두 함수가 섞였다.** `..` 검사는 `path_is_safe`(경로 → 403), 대소문자 약점은 `mime_type`(확장자 → MIME). 그리고 **파일 찾기 = www + 경로**가 빠졌다
3. **그래서:** `..`이 들어간 경로는 예외 없이 403
   - 바로잡은 것: 브라우저는 `..`을 미리 정리해서 보내므로 정상 사용자는 안 막힌다

3줄 쓰는 데 10분 걸렸다. 그 10분이 기억을 만드는 시간이다.

## 7. S4: POST 본문 끝까지 읽기 ✅

### 문제
머리는 빈 줄(`\r\n\r\n`)로 끝난다. 그런데 **본문 끝에는 아무 표시가 없다.** 본문 안에 아무 글자나 들어갈 수 있으니까.

### 해결: Content-Length
클라이언트가 머리에 **본문이 몇 바이트인지** 미리 적어 보낸다.
```
POST /echo HTTP/1.1\r\n
Host: localhost\r\n
Content-Length: 8\r\n          ← 본문은 8바이트
\r\n                           ← 머리 끝
name=jin                       ← 본문
```
응답에서 봤던 `Content-Length`를 이번엔 **요청 쪽에서 읽는** 것이다.

- `POST` = "이 데이터를 받아라". `/echo` = 우리가 정한 경로 이름. **받은 본문을 그대로 돌려준다** (본문을 끝까지 읽었는지 눈으로 확인하려고 정한 규칙)
- 본문도 조각나서 올 수 있다. `nam`만 왔으면 **기다린다.** main은 그 연결을 기다리며 잠들면 안 되고, `epoll_wait`로 돌아가서 **새 연결이든 다른 클라이언트의 데이터든 아무 할 일**이나 처리한다

### 통과 기준
| 보내는 것 | 기대 |
|---|---|
| 머리 + `name=jin` 한 번에 | 응답 본문 `name=jin` |
| 머리 + `nam`만 | 응답 없음 |
| 이어서 `e=jin` | 응답 본문 `name=jin` 1번 |

### head, clen, c->len (처음엔 이해 못 했다)
```
보관함:  [P O S T   / e c h o ... \r\n\r\n][n][a][m][ ][ ][ ][ ][ ]
          └─────────── 머리 ───────────────┘└────── 본문 자리 ──────┘

head   = 62   ← 머리가 몇 칸인가         (고정)
clen   = 8    ← 본문이 몇 칸이어야 하나   (고정, Content-Length 값)
c->len = 65   ← 지금 실제로 찬 칸 수      (조각이 올 때마다 늘어남)
```
- 목표 = `head + clen` = 70, 현재 = `c->len` = 65 → 5칸 비었음 → 기다림
- `head`와 `clen`은 **안 바뀌는 목표**, `c->len`만 **늘어나는 현재**

### 내가 쓴 조건 (두 번 만에)
| 시도 | 코드 | 결과 |
|---|---|---|
| 내 코드 전 | (조건 없음) | **너무 일찍** 응답 → FAIL |
| 1 | `if (clen != c->len + head)` | 다 왔을 때 넣어보니 `8 != 132` → 참 → **영원히 기다림** → FAIL |
| 2 | `if (c->len < head + (size_t)clen)` | **PASS** |

- 이번에도 **숫자를 넣고 따라가서** 원인을 찾았다
- 1차 시도에 `epoll_wait(...)`를 직접 불렀는데 필요 없다. `return`하면 main의 반복문으로 돌아가고, 거기 있는 `epoll_wait`가 다음 조각을 기다린다
- `(size_t)` = `clen`을 `c->len`과 같은 종류의 숫자로 맞추는 표시 (그냥 비교하면 컴파일러 경고)
- 테스트는 **내 코드 전에 FAIL**하는 것을 먼저 확인했다. 그래서 지금의 PASS는 내 코드 덕분이라는 증거다

### 찾은 약점: Slowloris
`Content-Length: 100`이라고 해놓고 8바이트만 보내고 가만히 있으면?
- 서버는 나머지를 영원히 기다린다. 다른 클라이언트는 영향 없다 (epoll)
- 그런데 **연결이 영원히 안 닫힌다.** 이런 클라이언트가 1,000개면 보관함 8KB × 1,000 = 약 8MB, 그리고 **연결 칸(1024)이 먼저 바닥나서** 정상 클라이언트가 접속을 못 한다
- 느린 클라이언트로 서버를 마비시키는 공격 = **슬로로리스(Slowloris)**
- 해결책: **timeout** (일정 시간 안에 안 보내면 끊기). 실험 01 때 이미 말했던 그 해결책이다

### 내 3줄 + 바로잡은 것
1. **본 것:** "POST에도 응답한다" → 바로잡음: 그건 S2부터 그랬다. 새로 생긴 건 **POST 본문을 Content-Length만큼, 조각나서 와도 끝까지 모은 다음에 응답한다**
2. **방법:** 본문이 다 왔는지는 현재까지 온 바이트(`c->len`)와 목표(`head + clen`)를 비교해서 판단한다 ✅
3. **그래서:** epoll 방식도 완벽하지 않다. 연결된 채로 일정 시간 안에 보내지 않으면 끊는 전략이 필요하다 ✅ (먼저 바닥나는 건 메모리보다 연결 칸)

## 8. 메타: 학습 전략과 내 규칙을 제대로 지키고 있었나
AI에게 "과학적으로 제대로 하고 있어? 내가 쌓은 규칙은?"이라고 물었다. 점검 결과:
- 잘 된 것: 인출 연습(카드), 섞어서 꺼내기(크롬 로그를 epoll로 설명), 자기 설명(3줄), 즉각 피드백(테스트)
- 안 된 것: 간격 반복의 시간표가 없었다 / 코드를 대부분 AI가 썼다 / 답변이 길어서 머리가 지끈거렸다 / 단계를 a·b·c로 나눈다는 걸 미리 안 알려줬다
- 원인: 마감에 끌려 진도를 앞세웠다 / 규칙이 많고 서로 부딪힌다 / 대화가 너무 길어졌다
- 고친 것: 단계 시작 = 지도부터 / **단계마다 코드 한 조각은 내가** / 카드는 오전 10시 + 퇴근 30분 전 / 질문은 자주, 대신 짧게

## 9. 오늘 배운 학습 방법
- **블로그를 읽기 전에 카드부터.** 먼저 읽으면 답을 보고 떠올리는 셈이 된다
- 정독할 때 "이걸 몰랐네", "백지에 설명 못 했을 거야"를 골라내면 그게 다음 카드가 된다
- **질문은 자주 받아도 된다.** 내가 제대로 이해하고 있는지 검증하는 것이다. 다만 질문은 짧게, 하나씩
- AI가 "다 돌렸는데 이상 없었다"고 하면 그건 내 검증이 아니다. **내가 돌리고, 각 줄이 무엇을 검사하는지 알아야** 내 검증이다
- 배우지 않은 숫자(403 같은)를 모르는 건 틀린 게 아니다. 추론이 맞으면 된다

## 10. 저녁 S6-a: 느린 클라이언트 1,100개로 서버 막아보기 ✅

### 왜 했나
S4에서 찾은 약점(Slowloris)을 **말로만 알고 와닿지 않았다.** 그래서 직접 붙여서 보기로 했다.

### 내 예측
"메모리가 아니라 **연결 칸**이 없어서 C는 연결이 안 될 것이다." 그리고 자리 수는 **fd 5~1023 = 1019개** ✅

### fd 번호 규칙 (관찰로 확인)
- fd 0·1·2 = 입력·출력·에러. **모든 프로세스가 시작할 때 이미 열려 있다 (표준)**
- fd 3·4 = 우리 서버가 listen 소켓 → epoll 목록 순서로 열어서 그렇게 된 것 (표준 아님)
- 커널은 **비어 있는 가장 작은 번호**를 준다 → curl이 반납한 fd 5를 다음 nc가 다시 받았다
- `epfd` = epoll fd = `epoll_create1`이 만든 "지켜볼 fd 목록"의 번호 (우리 서버에선 4)

### 실험 (터미널 3개)
| 터미널 | 역할 |
|---|---|
| A | 서버 켜기 + 로그를 화면과 파일(`/tmp/s6.log`)에 같이 남김 |
| B | 아무것도 안 보내는 느린 클라이언트(nc) 1,100개 |
| C | 정상 요청(curl) 1개 + 로그 세기(`grep -c` = 그 문장이 들어간 줄 수) |

### 결과
| | 수 | 이유 |
|---|---|---|
| 붙으러 온 클라이언트 | 1,101 | nc 1,100 + curl 1 |
| 자리 받음 (`연결됨`) | **1019** | fd 5~1023 |
| 쫓겨남 (`꽉 참`) | **82** | 나머지 nc 81 + 마지막에 온 curl 1 |

- 쫓겨난 82개는 **전부 fd 1024**였다. 1024를 받자마자 닫으니 다시 비고, 다음 클라이언트가 또 1024를 받는다 (예측은 1024, 1025…였는데 틀림)
- curl: `Connection reset by peer` → **C는 응답을 못 받았다** ✅
  - reset = 서버가 curl의 요청을 읽지도 않고 닫아서, 정상 종료 대신 **강제 종료**가 됐다는 뜻
- 커널은 fd 1024를 줬는데(ulimit 10240까지 줌), **우리 코드 `conn_open`이 `fd >= MAX_FDS`라서 거절**한 것

### 삽질: 처음엔 느린 클라이언트가 0개였다
- 내 터미널 셸은 **fish**라서 bash용 `for ...; do ...; done`이 실행되지 않았다 → 서버 로그엔 curl 하나뿐, 200 응답
- 고친 것: B에서 `bash`를 먼저 입력, 그리고 **실험 전에 `pgrep -c nc`로 1100개인지 확인**
- 교훈: 실험이 "아무것도 안 했는데 성공처럼 보이는" 경우가 있다. 준비물이 진짜 준비됐는지 먼저 센다

### 아직 이해 못 한 것 (내일 아침)
- timeout을 넣으려면 main이 **일이 없어도 가끔 깨어나야** 한다
- 지금 `epoll_wait(..., -1)`은 일이 생길 때까지 무한정 잠든다 → 1,019개가 가만히 있으면 main은 안 깨어난다 (A 로그가 멈춰 있는 것 = 이 상태)
- `-1` 대신 `1000`을 넣으면 "최대 1초만 잔다", 그때 아무 일 없으면 반환값 **n = 0** ← 여기서 막힘
