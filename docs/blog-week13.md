# [WEEK13] C로 epoll 웹 서버 + Reverse Proxy 만들기: 실험으로 확인한 것들

코드: https://github.com/YoonJinhoon/c-epoll-webserver

이번 주 목표는 C와 POSIX 소켓 API만으로 HTTP 웹 서버와 Reverse Proxy를 만드는 것이었다. 구현은 AI(Claude Code)와 함께 했다. 그래서 스스로 정한 규칙은 하나였다: **AI가 짠 코드를 맞다고 믿지 않는다. 예측하고, 실행하고, 로그로 확인한다.**

## 1. 동시성: 왜 epoll인가 (실험 4개)

같은 상황을 네 가지 서버에 걸어 봤다. 느린 클라이언트(연결만 하고 요청을 안 보냄)를 붙여 두고, 다른 클라이언트가 응답을 받는지 본다.

| 실험 | 방식 | 느린 클라이언트가 있을 때 | 원인 |
|---|---|---|---|
| 01 | 단일 스레드 | 서버 전체가 멈춤 | 스레드 하나가 그 연결의 `read`에서 블로킹 |
| 02 | 연결마다 스레드 | 안 멈춤 | 대신 연결 수만큼 스레드가 생김 |
| 03 | 스레드 풀 (Worker 2개) | 느린 클라이언트 **2개**면 멈춤 | Worker가 전부 느린 연결에 묶임 |
| 04 | epoll (스레드 1개) | 안 멈춤 | 데이터가 **이미 온** fd만 골라서 `read` |

세 방식이 멈춘 원인은 같았다. **"아직 데이터가 안 온 fd를 `read`하면 잠든다."** epoll은 커널이 "이 fd에 데이터 왔다"고 알려 준 것만 읽기 때문에 잠들지 않는다.

## 2. 진짜 서버 (`src/`): 단계별로 쌓기

| 단계 | 한 것 | 확인 |
|---|---|---|
| S1 | 요청이 여러 조각으로 와도 빈 줄(`\r\n\r\n`)까지 모아서 처리 | 두 조각으로 보내는 테스트 |
| S2 | 요청 라인 파싱. 형식 오류 400, 모르는 메서드 501 | 테스트 4개 |
| S3 | 정적 파일, 404, MIME 타입, **`/../src/main.c` 경로 탈출 차단(403)** | 먼저 직접 뚫어서 소스 코드가 나오는 걸 확인하고 막음 |
| S4 | POST 본문을 `Content-Length`만큼 끝까지 읽기 | 본문을 쪼개서 보내는 테스트 |
| S6 | 30초 동안 조용한 연결 닫기 (Slowloris 1차 방어) | 느린 클라이언트 1,100개 실험 |
| S5 | Reverse Proxy: `/api/*` → 백엔드 8001, 502, 504 | 대답 안 하는 가짜 백엔드 실험 |

연결마다 "보관함"(fd, 받은 바이트, 마지막 도착 시각)을 두고, 조각이 올 때마다 이어 붙이는 구조다.

## 3. 가장 기억에 남는 실험 두 개

### (1) 느린 클라이언트 1,100개로 서버 막기

- 예측: 연결 칸은 fd 5~1023, 즉 **1,019개**다 (0~2는 표준 입출력, 3은 listen 소켓, 4는 epoll).
- 결과: `연결됨` 1,019줄. 나머지는 fd 1024에서 바로 닫힘. 정상 클라이언트는 `Connection reset by peer`.
- timeout을 넣은 뒤: 30초가 지나자 1,019개가 전부 닫히고 정상 클라이언트가 200을 받았다.
- 왜 "보관함 전체를 훑나": 조용한 연결은 할 일이 없어서 `epoll_wait`의 `events`에 **한 번도 안 나온다.** 그래서 1초마다 깨어나 전체를 훑어야 한다.
- 아직 못 막는 것: 29초마다 1바이트씩 보내는 연결. 보낼 때마다 마지막 도착 시각이 갱신된다.

### (2) 대답 안 하는 백엔드 하나가 서버 전체를 멈춘다

- 상황: 백엔드 자리에 `nc -l 8001`(연결은 받지만 대답 안 함)을 띄우고 `/api/hello`를 요청. 그 상태에서 **백엔드와 상관없는** `/index.html`을 요청했다.
- 예측: "`/index.html`은 받는다" → **틀렸다.** 5초 timeout, 0바이트.
- 로그에서 읽은 것: 다른 클라이언트의 `연결됨` 줄이 **없었다.** accept조차 못 한 것이다.
- 원인: 프록시 코드가 백엔드 쪽 소켓을 epoll에 등록하지 않고 바로 `read`했다. 스레드 하나가 거기서 블로킹 → `epoll_wait`로 못 돌아감 → 아무도 못 받음. **실험 01과 같은 증상이었다.** epoll을 써도, epoll을 거치지 않은 `read` 하나가 서버 전체를 멈춘다.
- 고친 것: 백엔드 응답을 3초까지만 기다리고 504. 이제 3초 뒤에는 다른 요청이 처리된다. 근본 해결은 백엔드 fd도 epoll에 등록하는 것 (다음 단계).

## 4. 개념 정리

- **소켓의 실체는 커널 안에 있다.** 프로그램이 가진 건 번호(fd)뿐이다. 받은 데이터도, 아직 accept 안 된 연결도 커널 대기열에서 기다린다.
- **새 연결의 사슬:** 접속 → 커널이 listen 소켓 대기열에 넣음 → `epoll_wait`가 listen fd를 담아 돌아옴 → `accept`가 새 fd(비어 있는 가장 작은 번호)를 줌 → `epoll_ctl`로 감시 목록에 등록.
- **프록시는 양쪽 역할을 한다.** curl에게는 서버, 백엔드에게는 클라이언트다.
- **502와 504:** 502는 백엔드에 연결 자체가 안 될 때, 504는 연결은 됐는데 응답이 늦을 때.

## 5. 이번 주에 배운 공부 방법

**로그를 볼 때 순서대로 던지는 질문 5개**
1. 있는 줄: fd별로 묶으면 무슨 일이 어떤 순서로 일어났나?
2. 없는 줄: 있어야 하는데 없는 줄은?
3. 숫자: fd 번호와 바이트 수가 말해 주는 것은?
4. 멈춘 곳: 마지막 줄 다음 코드에서 누가 무엇을 기다리나?
5. 예측과 비교: 어떤 재료가 틀렸나?

**테스트가 거짓말한 기록도 남겼다.** 엉뚱한 서버가 켜져 있어서 PASS, `make`가 실패했는데 옛날 실행 파일을 테스트, fish 셸이라 반복문이 안 돌아서 느린 클라이언트가 0개였던 일, 엉뚱한 로그 파일을 센 일. 숫자가 예측과 안 맞을 때 멈춰서 따라가 보면 대부분 실험 쪽 실수였다.

**AI 코드에 던질 질문 하나:** "이 함수에서 기다리는 곳은 어디이고, 상대가 영원히 대답 안 하면 어떻게 되나?" Slowloris와 느린 백엔드 버그가 둘 다 이 질문으로 잡혔다.
